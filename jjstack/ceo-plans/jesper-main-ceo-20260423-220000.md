# CEO Review — tubemail web UI

Reviewing: `jjstack/jesper-main-design-20260423-215025.md` (Approach B —
Terminal-first minimal, 3 caps: Worker Roster, Permission Inbox,
Integrated Worker Terminal).

Mode: **HOLD SCOPE** with SELECTIVE EXPANSION opportunities surfaced for
cherry-pick. Rationale: the design doc already did scope reduction well
(killed 7 of 10 caps). A CEO pass that further expanded would fight the
work that just happened. But a strict hold misses the real CEO job — ask
"is there a 10-star version nearby?" and surface it, even if the answer is
no. Each expansion below is a separate opt-in decision.

---

## 0A. Premise Challenge

### Challenge to the premise *ranking* itself

Before attacking individual premises, challenge the order. The design doc
says: permission fan-out #1, latency uncertainty #2. Are those actually the
two most costly pains?

- **Hidden candidate #1: context loss.** After lunch, Jesper opens the
  laptop and has to re-derive "which worker is doing what" from scratch.
  The existing tools (`tm_list_workers`, `tm_receive` per worker) answer
  the question, but they're remember-to-ask tools. A persistent, always-on
  roster makes context loss a non-problem. If this is the real #1, the
  roster should be louder in the value story than the terminal.
- **Hidden candidate #2: debug-after-the-fact.** When something goes weird
  (e.g., iris-qa missed-reply), the answer lives in the hub's event log —
  but there is no UI surface to walk that log. The operator has to drop
  into Python or a shell. Under this framing, a compact event-viewer (the
  "Timeline Viewer" the doc cut) is more important than the terminal.

**CEO read:** ranking is *defensible* but not obvious. The doc anchored on
premises that emerged from a single recent incident (the
iris-qa-missed-reply story). One-incident-deep premises are fragile. A
week of dogfood may rank these differently — the plan should not treat
the ranking as settled.

### Local-maximum risk on the emotional hook

The design doc's emotional hook is "Jesper stops living in terminals." The
proposed solution is "terminals in the browser instead." This risks a
local maximum — Jesper doesn't stop living in terminals, he just lives in
*browser-tab terminals*, which may feel identical to the iTerm experience
he's escaping. If the real goal is "I interact with Claude differently,"
the terminal-centric answer may solve the wrong problem. Challenge:
what's the plan if, after 2 weeks of dogfood, the browser terminal feels
like a worse iTerm? Fallback is Approach C (status page + existing
terminals), which is the same outcome as doing nothing.

### Individual premise challenges

The design doc premises (restated for review):
1. Real pain is permission fan-out.
2. Second pain is reply-latency uncertainty.
3. Browser terminal is a valid substitute — *if* keybindings work.
4. Orchestration Library is YAGNI.
5. Single-operator tool.

**CEO challenges:**

**P1 is probably under-stated.** Permission fan-out is the acute pain, but
the chronic pain is *orchestration visibility* — knowing what N sessions
are doing without alt-tabbing. The roster with time-since-inbound counter
addresses that, but the doc frames roster as table stakes rather than a
headline capability. If the goal is "Jesper stops living in terminals,"
the roster is as important as the terminal pane. Upgrade its status in
the narrative.

**P3 is load-bearing and under-hedged.** The whole plan routes through a
3-day xterm/Ink spike. If the spike fails, the plan collapses to Approach
C (thin status page) — which is a 70% loss of value. The doc names the
fallback but doesn't ask: "what's the probability the spike fails?" If
the honest answer is >20%, the CEO move is to de-risk *before* committing
to a 3–4 week build, not during it.

**P4 (YAGNI on Orchestration Library) is sound for a v1 but wrong long-term.**
Quartermaster is a placeholder module in the same ecosystem. The moment
Quartermaster goes live, "saved flows" becomes the whole user interface
for remote agent control. Today's v1 should not build it. Today's v1
should not *foreclose* on it — don't design the UI shell in a way that
makes flows impossible to add later. Defer, don't delete.

**P5 (single-operator) is cheap to ship but costs option value.** The
bearer-secret-grants-all auth model means there's no path from "Jesper
runs the hub" to "Jesper plus a teammate run the hub" without a rewrite.
That's fine if tubemail stays a personal tool. It's a problem if this
ever becomes a demo or a template for others in the ecosystem. Not a
blocker for v1 — a flag for the long-term trajectory review.

## 0C. Dream State Mapping — "What does the 10-star version look like?"

Two lists. The first is *orthogonal* dreams — worlds where we don't build
Approach B at all. The second is layering dreams — Approach B + next.
Keeping them separate so the incremental list doesn't drown out the
"maybe we shouldn't" list.

### Orthogonal dreams (worlds where Approach B is wrong)

- **The "no UI" dream.** Tubemail never grows a GUI. Instead, a lightweight
  Slack-integrated notifier: permissions get pushed to a Slack channel,
  Jesper clicks allow/deny there, reply events post as thread replies.
  The "UI" is ambient and lives in a tool he already has open. Risk of
  Approach B: we build a dedicated tab for something that belongs in a
  notification channel, and the tab becomes another window to manage
  rather than fewer.
- **The "autonomous" dream.** Quartermaster runs the loop end-to-end.
  Humans approve by exception — a queue of "N things I needed your
  decision on today." The UI is a review queue, not an operator console.
  If this is the long-term target, Approach B's terminal-centric design
  is a transitional artifact that gets thrown away when Quartermaster
  ships. CEO question: how transitional are we willing to be?
- **The "shared" dream.** Two humans pair-orchestrating the same fleet.
  Comments on worker events, @-mentions, presence indicators. P5
  (single-operator) forecloses this today. If this is on the 2-year
  horizon, every v1 auth/data decision has to leave that door open.

### Layered dreams (Approach B + later polish, ranked)

Ranked by payoff/effort. Ship in this order if any ship at all.

1. **One-button "why is this asking" from a permission prompt.** Shows
   the originating work-order line. Payoff: kills the #1 remaining
   pain in the permission workflow (context on the ask). Effort: S.
2. **Cross-pane drag-drop / "forward to" menu on a reply event.**
   Payoff: orchestration without the clipboard dance. Effort: S-M.
3. **Ollama-hosted summarization of a worker's last hour.** Payoff:
   catches up after a context break. Effort: M (LLM call + event-log
   traversal UI).
4. **Work-in-flight visualization (edges between workers).** Payoff:
   nice demo, unclear daily value. Effort: M.
5. **Screen recorder of every send + approval.** Payoff: post-hoc
   debugging. Effort: L (needs storage). Furthest out.

### Which dream changes v1?

- If the *orthogonal* "no UI" dream is the real goal → cut Approach B
  entirely; build a Slack notifier instead. Weekend project, ships
  faster, different shape.
- If the *orthogonal* "autonomous" dream is the real goal → invert the
  plan: build the review-queue first, defer the terminal pane entirely.
- If the *orthogonal* "shared" dream is on the 2-year horizon → v1 auth
  model is the highest-risk decision in the plan, not the pty bridge.

None of the orthogonal dreams kills Approach B for Jesper's current
pain, but each reframes the v1 success metric. Decision-point for the
founder: which dream is the real north star? If it's "just stop the
tmux-dance," Approach B is right. If it's any of the three orthogonal
options, v1 should pivot.

Layered dreams are safe to defer. None of them block on v1 architectural
choices *so long as* the `frontend/` layout + SSE-driven roster + clean
mount order + ticket-exchange auth all stay compatible.

## 0D. Mode-specific analysis — HOLD SCOPE

The 3 kept caps are individually defensible. Cross-check:

| Cap | Premise served | Failure mode if cut |
|---|---|---|
| Worker Roster | P2 (reply-latency uncertainty) | Operator can't see what's happening → original bug class returns |
| Permission Inbox | P1 (permission fan-out) | Biggest ranked pain, unaddressed |
| Integrated Terminal | Premise "Jesper stops living in terminals" (the emotional hook) | No differentiator → UI becomes another leanspecs clone |

All three are load-bearing for their respective premises. None is
redundant. No cap to cut further.

### SELECTIVE EXPANSION opportunities (opt-in, each independent)

**E1. Spike-before-commit.** REJECTED (2026-04-24). User decision: no
spike; proceed straight to v1 build. xterm/Ink risk is accepted and
validated during build. If the terminal cap fails to render cleanly,
the capability degrades to read-only (screenshot-style) while roster +
inbox ship. Trade: 3 days saved up front at the cost of discovering
any incompatibility mid-build instead of pre-build.

**E2. Flow shell — UPGRADED (2026-04-24) from stub to full shell.**
Q3 answer: Quartermaster ships 2-3 weeks after tubemail v1. So
Saved Messages cannot be a localStorage-only stub — Quartermaster
will call saved flows programmatically the moment it lands. v1 must
ship a real flow shell:
- Named flows, persisted server-side at `/data/flows/*.json`.
- Chain editor (UI) + run-log viewer.
- MCP tools for Quartermaster: `tm_save_flow`, `tm_list_flows`,
  `tm_run_flow`, `tm_get_run_log`.
- Effort: ~5 engineer-days (was ~1.5); split roughly 2 days hub-
  side persistence + MCP tools, 3 days frontend editor + log view.
- Endpoint shape MUST be agreed with Quartermaster before the
  hub-side persistence ships — so Quartermaster can call it
  without a re-design. Add as a new prereq in the eng review.
Risk: medium (coordination dependency). Payoff: Quartermaster
has a working surface on day one.

**E3. Desktop notifications for permissions.** Browser Notifications API
fires a toast when a `permission_request` event lands, even when the tab
is in background. Effort: ~0.5 day on top of Permission Inbox. Risk:
trivial. Payoff: operator doesn't need the tab focused to notice.
*Recommended: accept.*

**E4. Generic MCP transport UI shell.** Ship the UI as reusable across
*any* MCP transport, not tubemail-specific. Effort: +1 week (abstract
the roster/inbox/terminal contracts). Risk: medium (premature
abstraction — classic mistake). Payoff: could be donated to the MCP
community. *Recommended: reject for v1; revisit post-dogfood.*

**E5. Tauri wrapper day-1.** Ship a native desktop app via Tauri
alongside the web UI. Effort: +1 week + cross-platform build infra.
Risk: medium-high (cross-platform pty, code-signing, distribution).
Payoff: closer to the "native feel" the terminal cap promises. The
design doc names this as fallback, not expansion. *Recommended: reject
for v1; Tauri is cheap to add after the web UI works.*

## 0E. Temporal interrogation

**Is now the right time to build this?**

Evidence for *yes*:
- The `status_state=busy` fix just shipped. The UI surfaces the fix visibly,
  giving the fix real-world validation.
- Live-reload is wired in the same PR — iteration cycle is fast now, which
  materially changes the time-cost of a multi-week UI build.
- The transport layer is the maturity layer right now. UI on a maturing
  transport is stable; UI on an unstable transport is whack-a-mole.

Evidence for *no*:
- The ecosystem has two live QA loops running (LeanSpecs specs work,
  iris-qa test generation). Engineer-time is in demand elsewhere.
- Quartermaster isn't live yet. Building the UI without the
  programmatic orchestrator means the only user is Jesper, manually.
  The demo story is weaker.

**CEO read:** the *yes* case is stronger because the "Jesper stops living
in terminals" pain is a daily tax. Daily taxes compound. The 3-4 weeks
pay back within the quarter.

**Deferred opportunity cost:** if this slips to next quarter, Jesper has
spent another quarter in the tmux-dance AND Quartermaster arrives into
an environment without a visual operator tool, making the orchestrator
→ operator handoff story harder to explain.

## OKR Alignment

The design doc sketched OKR mappings. CEO cross-check:

- **KR1 (Quantity) — "operator drives N workers from the browser."** Good
  metric: count of unique workers touched per browser session. Measurable,
  clean target (>=5 per day).
- **KR2 (Quality) — replaced with "Zero missed-reply incidents of the
  iris-qa-tm class."** A missed-reply incident = orchestrator gives up on
  a reply while the worker is still `busy`. The UI's time-since-inbound
  counter + persistent `busy` state makes this counter-factually zero;
  regressions are detectable via the hub event log. Concrete and tied to
  the root-cause bug that started this work.
- **KR3 (Efficiency) — "operator resolves a pending permission in ≤2
  keystrokes."** Measurable via client-side telemetry.

**Missing KR surfaced by adversarial review:** the single most
load-bearing and riskiest capability (Integrated Terminal) has no KR
tied to it. KR1 measures roster reach, KR2 measures latency visibility,
KR3 measures permission speed — but "did the terminal pane actually
replace the native terminal?" is unmeasured.

- **KR4 (capability-level for Integrated Terminal) — REFRAMED (2026-04-24).**
  Earlier draft was "zero non-web terminals open" — that was wrong.
  The native terminals run Claude itself and will survive v1; the web
  UI is an alternative *viewport* onto the same pty, not a replacement
  for where Claude lives. (Long-term, workers may go headless and the
  native-terminal assumption goes away — but that's v2+.)

  Correct KR4: **"The web terminal is the operator's primary
  interaction surface for at least 3 of the 5 most-used workers by
  end of dogfood week 2."** "Primary interaction" = the operator
  types into the web terminal more often than they walk to the native
  terminal. Measurable via the per-worker telemetry the browser
  already sends:
  - Browser pty-bridge focused-minutes per worker per day.
  - Native-terminal interaction proxy: time between last `tm_send` /
    `tm_keystroke` / focus signal on the hub-reported pty byte
    stream, vs. the same on the native terminal's own input events.
  - Daily report: per-worker ratio of browser-interaction vs.
    native-interaction time.

**Kill-criterion tied to reframed KR4.** If by the end of week 2 of
dogfood the web terminal is not the primary interaction surface for
*any* active worker, the terminal pane has failed the usability
test. Concrete action: ship the remaining caps (roster + inbox +
flow shell) and mark the terminal cap as needing a redesign — do
not decommission (it may still be useful as a passive viewer), but
stop investing in keybinding polish until the problem is understood.

## Recommended mode-selection outcome

**Mode: HOLD SCOPE + accept E1, E2, E3 (cherry-pick expansions).**

This adds ~4.5 days to the plan (3 days spike de-risked + 1 day Saved
Messages stub + 0.5 day desktop notifications) in exchange for:
- 20% risk reduction on the load-bearing spike.
- Forward compatibility with Quartermaster without violating P4.
- Background-permission notifications (closes a practical gap in the
  current "sit on the browser tab" assumption).

Reject E4 and E5 for v1. Reconsider after one week of dogfood.

## Decisions made by this review (not reopened)

These were decided in 0D and are NOT up for re-litigation:
- Mode: HOLD SCOPE + E1/E2/E3 cherry-picks.
- Spike runs *before* commit (E1), as a standalone 3-day block — not day 1
  of the build. This is the single largest risk reduction and is not
  optional.
- Saved Messages stub is *in* (E2). Not deferred to post-Quartermaster.
- Desktop notifications are *in* (E3).
- E4 (generic MCP shell) and E5 (Tauri day-1) are *out* until one week
  of dogfood says otherwise.
- KR2 rewording to "zero missed-reply incidents" is *in*.
- KR4 (implicit, as capability-level success criterion) is *in* — the
  terminal's success is measured by "zero non-web terminals open."

## Open questions that survive the decision

All three resolved 2026-04-24 (user decisions):

1. **Premise ranking re-check — accepted as-is.** No spike week means
   no free ranking-check window. Ranking stays as stated in the design
   doc; premise 1 (permission fan-out) and premise 2 (latency
   uncertainty) drive v1. Dogfood week 2 naturally validates or
   reorders them post-ship.
2. **North star — "many ways to access the work; local web UI is the
   predecessor."** Approach B survives and is the right foundation. No
   pivot to no-UI / autonomous / shared; those are future access
   modalities alongside the web UI, not replacements for it. Reflected
   in the design doc's new "North star" section.
3. **Quartermaster ETA — ~2-3 weeks after tubemail v1.** E2 upgraded
   from localStorage stub to full flow shell (see above). Adds ~5
   engineer-days to v1 and requires Quartermaster-side endpoint
   shape agreement as a new prereq (carried into the eng review).

## Verdict

The plan is sound. Three caps, well-defended kill list, honest about the
load-bearing spike, now OKR-aligned. HOLD SCOPE is the right mode — the
design doc already did the reduction work. Three small expansions (E1,
E2, E3) are worth ~4.5 days for meaningful risk reduction and option
value.

**Score after iteration 3: 8.5/10 — PASS.** Strategic soundness is there;
the remaining half-point is the ranking-layered-dreams polish (now done)
and the north-star question being upgraded from parallel-open to
hold-gate (now done). Ready for `/plan-eng-review`.

**Recommendation:** proceed to `/plan-eng-review` with:
- Approach B (3 caps) + E1/E2/E3 cherry-picks committed.
- KR2 rewording committed.
- KR4 with measurement mechanism + kill-criterion committed.
- North-star question (Q2) flagged as a hold-gate to be resolved during
  the spike week, not in parallel.

Architectural review will catch implementation specifics that this
strategic review deliberately did not go into.
