## Architecture as-built

```
src/tubemail_hub/
├─ server.py               (FastAPI + FastMCP + lifespan + static SPA)
├─ recorder.py             (RecordingManager + WorkerRecording)         [451 lines]
├─ config.py               (HubConfig — pydantic JSON persist)          [74 lines]
├─ refresh.py              (refresh_tools MCP convention)
├─ health.py               (KPI-shaped /health response)
├─ bridge/
│  ├─ engine.py            (BridgeEngine — in-memory state + SSE)       [787 lines]
│  ├─ models.py            (Pydantic, status_state with busy decay)     [119 lines]
│  ├─ http.py              (forwarder-facing /tubemail/*)
│  ├─ api.py               (frontend-facing /api/*, /api/settings)
│  ├─ ws.py                (WebSocket pty bridge + ticket exchange)
│  ├─ pty_registry.py      (browser fan-out + recorder tee)
│  ├─ tickets.py           (single-use 30s tickets for ws auth)
│  ├─ flows.py             (FlowStore — saved templates)
└─ tools/
   ├─ workers.py           (28 MCP tools, mostly tm_*)
   └─ flows.py             (flow MCP surface)
```

This shape is good. Module boundaries match responsibilities; no module is
doing two unrelated things. `engine.py` at 787 lines is the largest, which
is correct — it's the in-memory state authority. The bridge subdirectory
holds all the wire-protocol code (HTTP, SSE, WS); `recorder.py` and
`config.py` are at the top level because they're concerns the bridge uses
but doesn't own.

**One observation, not a fix:** `engine.py` mixes three responsibilities —
state CRUD (`register_worker`, `goodbye_worker`, `purge_worker`), event
recording (`enqueue_inbound`, `record_outbound`, `record_permission_*`),
and SSE fan-out (`subscribe`, `subscribe_all`, `_fan_out*`). It works, but
if a fourth responsibility lands (e.g., something around recording
coordination) the file will start feeling like a god-object. Watch the
slope. Today: don't refactor.

## E1. The SSE eviction loop and the pty_attach streaming bug

### What the as-built doc says

> Recording requires the manager to push PTY bytes to `/pty-out`. The
> manager only does this when it receives a `pty_attach` SSE event...
> The fix attempts to fire `pty_attach` when recording is toggled on...
> The hub-side wiring landed but does not appear to be reaching the
> manager for browser-less workers. A pre-existing eviction loop ... is
> suspected to be eating the events.

### What's actually happening

Two separate problems are tangled here. They look similar but have different
fixes.

**Problem 1: subscribe() evicts existing subscribers.** `engine.py:702-713`:

```python
existing = self._outbound_subscribers.get(worker, [])
if existing:
    _log.warning("subscribe: evicting %d existing subscriber(s) for %s — duplicate session detected", ...)
    for old_q in list(existing):
        try:
            old_q.put_nowait({"event": "closed", "data": {"reason": "superseded"}})
```

This fires *every time* the manager re-subscribes (e.g., SSE reconnect,
hub reload). The hub logs in the as-built doc show it firing 4 times in
~200ms for `architrix-tm` — which suggests the manager is reconnecting
SSE in a tight loop, OR the channel plugin (running inside claude) is
also subscribing to the same name as the manager.

Let me check that hypothesis. The manager registers as
`<worker>-manager` and subscribes to `/tubemail/<worker>-manager/stream`.
The channel plugin (inside claude) registers as `<worker>` and subscribes
to `/tubemail/<worker>/stream`. They use *different* worker names. If both
are evicting each other under the *same* name, something's wrong.

**Looking at the hub log evidence:**
```
GET /tubemail/architrix-tm/stream     ← someone subscribes for architrix-tm (the worker, not the manager)
subscribe: evicting 1 existing subscriber(s) for architrix-tm
POST /tubemail/architrix-tm/register  ← then re-registers
GET /tubemail/architrix-tm/stream     ← subscribes again
subscribe: evicting 1 existing subscriber(s) for architrix-tm
```

This is the **channel plugin** (inside claude) — not the manager — evicting
itself. Two channel-plugin instances are both trying to subscribe to
`architrix-tm`'s SSE stream, each closing the other's. That's a classic
"old connection wasn't fully torn down before new one started" pattern.

**Most likely root cause:** the channel plugin opens a new SSE before the
old one's TCP socket has been GC'd, the hub sees both at the registry-data
level and evicts the older. The eviction sentinel triggers the channel
plugin to reconnect (interpreting "closed" as "I should retry"), and the
loop self-perpetuates.

**Problem 2: my pty_attach streaming wiring assumes a stable subscription.**
`engine.py:1` (the new `_sync_pty_stream` method) calls
`_fan_out(manager, {"event": "pty_attach", ...})`. If the manager's SSE
just got evicted between when I fire the event and when the manager
re-subscribes, the event lands on a queue that's about to be closed —
delivered as `{"event": "closed", ...}` to the manager, who interprets
it as "no clients" and stops streaming.

**Recommended fix sequence:**

1. **Fix Problem 1 (SSE eviction loop) first.** It predates the recording
   feature and is the load-bearing bug. Two paths:
   - **Cleanest:** add a "fan-out, don't evict" mode to `subscribe()`.
     Multiple subscribers for one worker is fine — the channel plugin
     and the hub UI's roster could both subscribe and both want events.
     Eviction was added in the 2026-04-16 incident comment as a fix for
     duplicate-session inconsistency, but the cure may now be worse than
     the disease.
   - **Defensive:** keep eviction, but add a "still-warm-grace" of 500ms
     before an existing subscriber is evicted. Reconnects within the
     grace window are treated as the same session and don't trigger
     eviction.
   - **Verify which:** `git blame` the eviction block, read the
     2026-04-16 incident note, check if "duplicate session" was a real
     pathology or a defensive guard against a now-fixed issue.

2. **Fix Problem 2 (race between pty_attach and resubscribe).** Once the
   eviction loop is gone, `_sync_pty_stream`'s pty_attach event will land
   on a stable subscription. Verify by toggling recording on a
   browser-less worker and confirming `.cast` files start growing.

3. **Add a regression test.** The existing test suite covers the engine
   in isolation, not the manager round-trip. A fixture that simulates
   the channel plugin's SSE subscribe + reconnect would catch eviction-loop
   regressions deterministically. Hard to write; worth it because the
   bug surfaced through hub log archaeology, not a failing test.

### What's NOT broken

- `_sync_pty_stream` itself is correct logic: "wants_recording or
  has_browsers → fire pty_attach; neither → fire pty_detach." This is the
  right shape. The bug is upstream of it.
- `pty_registry.has_any_client()` extension to count recording is correct.
- `ws.py`'s "don't fire pty_detach if recording is on" check is correct.

So the *direction* of the recording streaming wiring is fine. The fix is
bunked behind the SSE eviction bug.

## E2. Recording wiring: engine method vs separate coordinator?

The user asked: should `_sync_pty_stream` live on `BridgeEngine`, or in a
separate `PtyStreamCoordinator`?

**Recommendation: keep it on `BridgeEngine` for now. Extract when a third
subscriber type appears.**

The reasoning:

The pty stream has two demand sources: browsers (counted by
`pty_bridges.attached_count`) and the recorder (counted by
`recorder.is_recording`). Both signals belong to objects the engine already
has references to. The "fire pty_attach when total > 0, pty_detach when
total == 0" logic is one method. Externalizing it to a coordinator class
would create three objects (engine, recorder, coordinator) where two work
fine.

**The smell that would force extraction:** if a third "wants stream"
source appears (e.g., a transcript-export feature that taps the live
stream, or a hub-side tail tool), and the engine starts collecting yet
another reference. At that point the coordinator pays back. Today it's
two sources, both already engine-known.

**Smaller refactor that does pay back today:** rename `_sync_pty_stream` to
something more verb-like — `_refresh_pty_stream_state` or just `_repump_pty`.
"Sync" is overloaded with "synchronization primitive" and the method name
doesn't tell you it might fire an SSE event with side effects. Method
naming is cheap to fix.

## E3. `WorkerState.recording_enabled` and `context_pct` — state or derived?

The user flagged: should these fields live on `WorkerState`, or be derived?

**`recording_enabled`: keep as state. Correct as-is.**

Reasoning: `recording_enabled` IS the source of truth — it's what the
operator toggled, what gets persisted across hub restarts, what
determines whether the recorder is active. Deriving it from
`recorder.is_recording(name)` would invert the dependency: the recorder
would own the toggle, but the recorder is a runtime object that knows
nothing about persistence. Today, on restart, `_load_all` reads
`recording_enabled` from disk and calls `recorder.start(name)` to
re-engage. That's the right direction.

The only smell here is that the coupling between `WorkerState` and
`recorder` lives implicitly in `register_worker()` and
`set_recording_enabled()` rather than as an explicit "sync layer." A
future engineer could add a third place that mutates one without the
other. Mitigation: a 3-line invariant test that asserts
`ws.recording_enabled == recorder.is_recording(ws.name)` after either
operation. Cheap, pays back the first time someone forgets.

**`context_pct`: keep as state, but flag it.**

This one's borderline. The value is parsed by the manager every 3s and
POSTed to `/tubemail/<worker>/context-pct`. It's stored on `WorkerState`
and persisted. That's three layers of state for what is essentially a
cache of a screen-buffer parse.

The argument for keeping it as state:
- Roster updates need to reach the frontend without a per-render parse.
- After hub restart, the frontend should show the last-known value
  immediately, not a `—` until the manager next pushes.

The argument against:
- It's persisted via `_persist(name)` on every change. If the worker is
  active and changes context % every minute (e.g., an ongoing edit-test
  loop), that's 60+ disk writes per worker per hour. Across 14 workers
  that's a non-trivial disk thrash on the persisted JSON files for what
  is *cached* data.

**Recommendation:** keep it on `WorkerState` (the persist-is-fine-most-
of-the-time path) but split the persistence: `recording_enabled` is
load-bearing and persists immediately; `context_pct` is a hint and
persists on a debounce (e.g., at most one persist per 30s, or only when
the worker would have been persisted anyway for another reason). The
disk-write reduction is real and the data loss on hub crash (last 30s of
context % values lost) is meaningless because the manager re-pushes the
current value within 3s of restart.

This is an optimization, not a correctness fix. File it as "watch and
optimize when persist frequency becomes a profile finding."

## E4. Busy-decay in pure-model `status_state()` — good or smell?

**Verdict: clean code, mild smell.**

The decay rule:
```python
if self.events and self.events[-1].kind == "inbound":
    if time.time() - self.events[-1].ts > BUSY_DECAY_S:
        return "idle"
    return "busy"
```

What's clean:
- Logic lives where it should (next to the data it computes from).
- Pure function in spirit — the only impurity is `time.time()`.
- The constant `BUSY_DECAY_S = 600` is at module scope, importable for
  tests. Tests use it (`tests/test_bridge_engine.py:test_status_state_decays_old_inbound_to_idle`).

What smells:
- A method that calls `time.time()` is no longer pure. Two consecutive
  calls can return different values. Most of the time that's what you
  want. Some of the time (e.g., serializing a worker for an API
  response) you want a snapshot. The `list_workers()` API takes the
  current value at the moment of serialization, which is fine, but a
  reader might expect `status_state()` to be a function of the data.

**The cleaner shape:** make `status_state()` accept an optional `now: float`
parameter (default `time.time()`). Tests can pass deterministic values;
production calls pass nothing and get current time. Cost: 2 lines of
code, immediate testability win, no smell.

```python
def status_state(self, now: float | None = None) -> str:
    now = now if now is not None else time.time()
    if self.pending_permissions:
        return "waiting_permission"
    if self.events and self.events[-1].kind == "inbound":
        if now - self.events[-1].ts > BUSY_DECAY_S:
            return "idle"
        return "busy"
    return "idle"
```

That's a 2/10 risk improvement, not a 10/10 — but it's free.

## E5. `HubConfig` + `load_config` + `save_config` — simplicity vs `shared/config`

The user asked: is a 74-line custom config file justified vs using
`shared/config/BaseConfig`?

**Recommendation: keep the local HubConfig. Don't pull in shared.**

Reasoning:
- `BaseConfig` (per the original `/plan-eng-review`) is a heavier object:
  Fernet encryption, env-var overrides, `_updatable_fields` allow-list,
  cached instances. Tubemail's hub config has none of those needs —
  three plain bools/ints, no secrets, no env override pattern in use.
- `tubemail-hub`'s `pyproject.toml` doesn't depend on `disciplin-run-shared`.
  Adding the dep to use BaseConfig pulls in cryptography, the auth
  module, the LLM module, etc. That's a 50+ MB dep tree increase to
  save 50 lines of code.
- The custom file is 74 lines because Pydantic does most of the work
  (model_validate_json, model_dump_json). It's idiomatic Python.

Exceptions:
- If a future hub setting needs to be *encrypted* (e.g., a third-party
  API key for some downstream use), reach for `BaseConfig` — that's where
  the value pays back.
- If three+ MCP services in the monorepo all define the same shape of
  hub config, lift to `shared`. Not yet.

What I'd do at the file level:
- Rename `_config_path` to drop the underscore (it's used by the public
  `load_config` and `save_config`, not internal).
- Document the corrupt-file fallback behavior in the module docstring
  (currently it's only on `load_config`'s comment) — operators should
  know that a malformed `hub-config.json` causes silent revert to
  defaults with a warning log.

## E6. `tm_reconnect_mcp` — the blind-keystroke design

The user named this as a concern. The as-built doc records the bug:

> Each step is screen-aware in a weak sense (it has a 5s wait for a
> string match). Cursor position is not verified after each arrow, the
> detail-menu detection is brittle, and the "type 2" assumption is wrong
> for non-OAuth servers where Reconnect may be option 1.

**Engineering verdict:** the current design has three separate failure
modes:

1. **Arrow-key drift.** `for _ in range(pos): os.write(master, b"\x1b[B")`
   with a `time.sleep(0.15)` between presses. If any arrow is dropped or
   debounced by the TUI, the cursor stops short. No verification.

2. **Detail-menu false negatives.** `lambda s: "Reconnect" in s and
   ("Authenticate" in s or "Disable" in s)`. A non-OAuth server's detail
   menu may not contain "Authenticate". And "Disable" is contextual —
   may not always be present. The wait fails, Esc is sent, dialog closes.

3. **"Type 2" assumes a fixed menu order.** OAuth servers might have
   `1. Authenticate, 2. Reconnect, 3. Disable`; non-OAuth might have
   `1. Reconnect, 2. Disable`. Same keystroke gets different results.

**Recommended rewrite (sketch only — user said no new features, but the
existing feature is broken):**

- After each arrow keypress, parse the screen to find the line starting
  with `❯ ` and verify the cursor moved one row in the expected
  direction. Bail out if the cursor didn't move.
- After Enter on a server, parse the detail menu to find the option line
  matching "Reconnect" (case-insensitive) and read its number. Type that
  number, not a hardcoded `2`.
- Use longer timeouts on the *initial* "did the dialog appear" check
  (5s is too tight when the worker is busy).

This is a behavior fix for an existing tool, not a new feature. Worth
doing because the recording feature was added to debug long-running
sessions, and `reconnect_mcp` failures are a top-N reason a session needs
to be debugged. Compounds.

## E7. The sortable-columns / ctx-column / busy-decay UX adds — engineering quality

Quick passes on the three UX adds:

**Sortable columns** (Roster.tsx `sortWorkers`): solid. Tabular numerics
on the sort comparators (`a.context_pct - b.context_pct`), nulls sort
last regardless of direction (correct), name fallback as tiebreaker
(correct). One nit: the `STATE_ORDER` map at module scope means a
typo'd state silently sorts to position 99. Acceptable; alternative
(exhaustive switch) is more code.

**Ctx column**: backend has the `update_context_pct` engine method, the
`/tubemail/<worker>/context-pct` endpoint, the manager-side
`_context_pct_loop`, and the `_CONTEXT_PCT_RE` regex. All clean. The
3-second poll cadence is conservative (claude renders the status bar
infrequently); could go to 1s without much cost. Don't bother.

**Busy decay**: covered in E4.

## E8. Test posture — what's covered, what's not

Hub: 138 tests pass, including the new busy-decay test and the recorder
test suite (start/stop/rotate/keep-files/grep/limit). Channel: 58 tests
pass.

**Coverage gaps worth flagging:**
- No integration test for the recording → manager-streaming round-trip.
  That's the bug area. Hard to write because it needs a running
  manager process; the gap is honest.
- No test for `engine._sync_pty_stream` firing the right event at the
  right moment. Could be a unit test with a mock pty_bridges +
  recorder. ~10 lines, would have caught the streaming bug if it were
  an event-content bug rather than an SSE-eviction bug.
- No test for `tm_reconnect_mcp` end-to-end. Existing tests cover only
  the parsing helpers (`_extract_mcp_server_list`, `_server_dialog_position`).
  The orchestration logic is untested.

## E9. CI / build / shipping

- `entrypoint.sh` runs `uvicorn --reload` always (including production).
  Per the as-built doc note: this is a documented choice (single-entrypoint
  variant the team picked over the compose-override pattern). Cost: file
  watcher overhead in prod (negligible at this scale). Benefit: simpler
  entrypoint for ops.
- `.github/workflows/test.yml` is in the staged-changes list (per
  `git status`). Engineering haven't reviewed the file content, but the
  file exists. Worth verifying the frontend build (vite) is gated on
  PRs. The original eng review called this out.
- Frontend `package.json` is at `frontend/`, not the repo root. Bind
  mount in compose is `./frontend/dist:/app/frontend/dist:ro` — host
  must run `npm run build` before changes appear in the container. Not
  hot-reload. Documented.

## E10. The big-picture engineering call

**Tubemail-as-shipped is a healthy codebase.** The shape matches the plan,
the modules have clear boundaries, the test posture is good for the
covered surface, and the live-reload setup makes iteration fast.

The one fix that would make it a clean 9 is closing the SSE eviction
streaming bug. That's the only "real" bug. Everything else in this review
is a preference, an optimization, or a smell that compounds slowly.

If you can only fix one thing this week: **fix the SSE eviction loop.**
That single fix:
- Makes recording work end-to-end as the feature claims.
- Eliminates the file-rotation thrash observed during debug.
- Probably resolves the spurious manager re-registers we've been seeing
  in the logs.
- Pays back compounding interest because every future feature that
  touches SSE inherits the bug-free baseline.
