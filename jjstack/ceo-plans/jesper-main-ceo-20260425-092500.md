## 1. The two scope adds — assessed

### 1.1 Saved Flows (Cap 4) — defensible

Premise 4 said "saved flows is YAGNI in v1." The premise was overruled. The
as-built doc records why thinly: "the orchestrator side wanted a
programmatic way to invoke named templates; the operator side wanted the
same templates accessible from the UI; one store, two clients."

CEO read: this is a fine reason. Two distinct users (operator + orchestrator)
asking for the same primitive is exactly when YAGNI flips. The original
review even flagged this as "Defer, don't delete" — the foreclose risk was
named. The team didn't foreclose; they let the second user materialize and
shipped the cap. That's the right shape of decision.

What's missing: a one-paragraph note in the as-built doc explaining when
the second user (orchestrator) actually showed up. If it's "Quartermaster
is using flows in production," the override is fully justified. If it's
"we anticipated Quartermaster might want this," the override was preemptive
and worth a retro. The doc says "the orchestrator side wanted" — a vague
"wanted" is weaker than a specific "X used it for Y." Tighten the
attestation.

### 1.2 Recording (Cap 6) — flagged as scope-creep-without-review

Recording was not in the original 10-cap proposal, the cut list, the kept
list, or the v1.5/v2 sketch. It appeared during the build window. The
as-built doc rationalizes it as "the operator needed a way to debug a
long-running worker session after the fact, without sitting at the popout
terminal in real time."

That's a real pain. But two things:

1. **The pain wasn't in the premise list.** The original premises ranked
   permission fan-out (P1) and reply-latency uncertainty (P2). Post-mortem
   debugging was not surfaced as a top-N pain. Either it should have been
   (and the premise list missed it), or it shouldn't have been (and the
   feature is over-built relative to the actual pain).
2. **The feature shipped with three load-bearing pieces — config
   persistence, per-worker toggle, MCP tool surface — and a settings page
   to manage them.** That's a meaningful surface area for a feature that
   wasn't on the v1 list. By contrast, "Health & Observability dashboard"
   was explicitly cut for being too much.

CEO challenge to the trajectory: was recording really worth ~the same
implementation budget as Permission Inbox? If yes, the original premise
list was wrong (it should have ranked debug-after-the-fact higher — which
the original CEO review actually flagged: "Hidden candidate #2:
debug-after-the-fact"). If no, recording is over-invested for a v1 nice-to-have.

**My read:** the original CEO review specifically called out
debug-after-the-fact as a possibly-mis-ranked pain. Recording validates that
flag. So the override is not creep; it's the team listening to the dogfood
signal. **Verdict: justified, but worth a one-line attestation in the doc
so the trajectory of "we promoted X from off-list to v1" stays legible to
a reviewer six months from now.**

What's NOT justified is the streaming bug. Recording shipped in a
state where it doesn't fully work (browser-less workers don't capture).
That's the kind of bug that should have caught a feature before it left
"in progress." Either the feature should have been gated on "works without
a browser" or it should have shipped with a known-limitation note in the
Settings page. Currently it ships as if it works.

## 2. The state-machine decay (BUSY_DECAY_S)

Added 2026-04-25. The original state machine table had no decay rule. The
fix is correct and well-tested. The CEO concern is the *discovery path*:
this bug sat for two days on jjstack-tm before the operator noticed.

That tells me one of two things:
1. The roster's "busy" state isn't checked often enough that a stuck-busy
   gets noticed quickly. (Plausible — it was visible in the screenshot but
   nobody flagged.)
2. The original premise 2 ("reply latency uncertainty is the second pain")
   was correct, but the *symptom* — stale-busy — wasn't being treated as
   the same problem. The same operator who would have flagged "iris-qa-tm
   silent for 60 seconds" didn't flag "jjstack-tm busy for 2 days."

Both readings suggest the same fix: **the roster needs to surface
"persistently busy" as visually distinct from "recently busy."** A worker
busy for 5 minutes is normal. A worker busy for 5 hours is suspicious. Right
now both render the same way (amber + counter). A subtle visual escalation
(e.g., counter font weight or color shift past 1 hour) would have caught
this earlier.

This is a small UX change, not a CEO scope expansion. Filing as a
trajectory observation rather than a recommendation, because the user said
no new features.

## 3. Settings page — within bounds, watch the slope

The original plan said "Cut Admin & Auth UI." The as-built has a Settings
page with three knobs (recording default, max bytes, keep N) plus sign-out.

CEO read: this is fine. Two of three knobs serve the recording feature; the
third manages the same. The page is small (one screen, no nav) and serves
a real purpose. It doesn't violate the original "cut" — that cut was about
not building admin/auth, and admin/auth is still not built.

**Slope concern:** every shipped feature wants a settings panel. Recording
got three knobs. If the next feature (whatever it is) wants two more
knobs, the page will fragment unless we put a structure on it now. Today
it's a flat list. At 5+ knobs it needs sections + descriptions. Worth
flagging to /plan-design-review rather than CEO.

## 4. The trajectory question — is tubemail still a transport-only library?

The original `README.md` says: "Not an orchestrator. TubeMail is the
plumbing." That positioning predates the web UI, the recording feature,
saved flows, and the settings page.

CEO question: **as built, is tubemail still a transport library, or is it
becoming an operator console?**

The shipped surface argues for "operator console":
- 28 MCP tools (vs the original "send/receive/restart primitives, nothing more").
- A web UI with five tabs (Workers, Permissions, Saved Messages, Settings,
  + the per-worker terminal pane).
- Per-worker recording with persistent files.
- A flow store with run logs.
- An "update manager" path with safety gates.

This is not the README's "plumbing." It's a control surface for fleet
operations. That's fine — and probably good — but the positioning needs
to catch up. The README still pitches "the plumbing" while shipping
"the cockpit."

**Two possible fixes:**

A. **Trim the surface back to the README's promise.** Move the web UI,
   recording, and flows out of `tubemail-hub` and into a separate
   "tubemail-console" package. Tubemail proper stays minimal. Cost:
   real refactor, breaks the live-reload setup, requires a second
   deployable.

B. **Update the README to match what's shipped.** Acknowledge that
   tubemail is "transport + an operator surface for the transport,"
   keep the orchestration-policy line out of scope, but stop pitching
   it as raw plumbing.

CEO recommendation: **B.** The shipped surface is in service of the
plumbing — the web UI exists to drive workers, the recording exists to
debug workers, the flows exist to send to workers. None of it implements
orchestration *policy* (failure routing, retry, scheduling, load
balancing). The plumbing claim is still true at the policy layer; it's
the UX layer that grew. A README update closes the gap honestly. It also
forecloses the option-value of tubemail-as-library — that's a tradeoff
worth flagging, but I don't see anyone consuming tubemail-without-the-UI
yet, so the foreclosure cost is theoretical.

**Open question for the user:** do you want tubemail to remain installable
as just the transport (no UI, no recording), for use as a library by other
projects? If yes, A. If no, B.

## 6. What's NOT in scope for v1.5

Resisting the temptation to expand. The original review's "v1.5 / v2
sketches" were:
- Persistent permission rules
- Health KPI dashboard
- Event-log search / Timeline Viewer
- Multi-operator collaboration

None of these have moved. The recording cap that *did* ship is arguably
the most useful of the v1.5 candidates — it's debug-after-the-fact, which
addresses the "Hidden candidate #2" the original CEO review flagged. So
the team's instinct on prioritization tracks the original review's
hidden-candidates list more closely than the original *premises* list.

**Trajectory note:** when the team picks features, they're tracking the
"this is annoying me right now" signal more than the "we wrote down the
premises" list. That's fine for a personal tool. It would not be fine for
a multi-stakeholder product. A retro question: do we want to *update the
premises* with what the dogfood actually surfaced, or keep the premises
aspirational and note the dogfood divergence?
