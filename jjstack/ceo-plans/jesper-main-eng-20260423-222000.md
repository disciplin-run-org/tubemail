- CEO plan: `jjstack/ceo-plans/jesper-main-ceo-20260423-220000.md` (HOLD + E1/E2/E3)

Status: **Ship with 6 architectural corrections.** No blocking defects. The

implementation-level assertions in the design doc are wrong or under-spec'd;
naming them here saves the first build day.

## Architecture at a glance

The web UI lives **in the existing tubemail-hub container**. It adds:

- **One frontend bundle** served at `/` (replaces the current HTML landing page).
- **Four new HTTP endpoints** on the hub for the UI's own needs.
- **One new WebSocket endpoint** on the hub for pty bridging.
- **One new outbound event type** on the forwarder/manager SSE back-channel:
  `pty_data`. This is how bytes get from the manager's pty to the hub, and
  how the hub pushes browser keystrokes back to the manager.

No new services, no new ports, no new process. All new surface is on the
hub's existing port 8004 under HTTPS-if-certs-else-HTTP (existing pattern).

```
browser  <─── WSS /ws/pty/<worker>?ticket=...  ───>  hub
                                                      │
                                                      ├── existing SSE /tubemail/<worker>/stream
                                                      │        (per-worker forwarder feed)
                                                      │
                                                      └── new event-kind `pty_data` pushed
                                                           to that worker's forwarder
                                                           (forwarder == manager process)

manager  ── POST /tubemail/<worker>/pty-out  ──>  hub (new endpoint)
           (manager writes pty output → hub fans to all browser WSes)
```

## Prerequisites — three small engine-correctness fixes before v1 work

Three small fixes bundled into one PR that must land before any of
the new capability code:

### Prereq A — existing `_fan_out` violates no-silent-errors rule

Before building anything new on top of the engine's SSE fan-out,
fix the existing silent drop:

```python
# src/tubemail_hub/bridge/engine.py:321-327 (current)
async def _fan_out(self, worker: str, message: dict[str, Any]) -> None:
    subs = self._outbound_subscribers.get(worker, [])
    for q in subs:
        try:
            q.put_nowait(message)
        except asyncio.QueueFull:
            pass   # ← silent drop, violates CLAUDE.md no-silent-errors
```

A slow subscriber silently loses events. For v1's pty traffic (high
volume, low-latency) this would surface as "occasional missing
keystrokes, no error." Fix before anything new touches the fan-out:

```python
except asyncio.QueueFull:
    _log.warning(
        "_fan_out: subscriber queue full for %s, closing slow subscriber",
        worker,
    )
    # Schedule removal; do NOT pass silently.
    q.put_nowait({"event": "closed", "reason": "queue_full"})
    # Caller's iterator sees the sentinel and terminates.
```

One-line fix, 10-minute PR.

### Prereq B — bearer comparison must be constant-time

`http.py:31-47` compares bearer tokens with `==`. Timing-attack surface
is small today (single operator) but will broaden as soon as the web
UI ships — any browser with a bad token becomes an attacker probe.
Replace with `hmac.compare_digest`. 5-line PR.

### Prereq C — `record_outbound` and `record_permission_response` do not fan out

Already covered in the Correction 6 engine-additions above. For the
prerequisite PR: add one `_fan_out` call per function. This is
additive — the existing forwarder SSE ignores these events (they
originate from the forwarder), so the change is invisible to the
forwarder and enables the future global subscriber.

### Prereq D — flow-shell endpoint shape agreed with Quartermaster

Added 2026-04-24 after E2 upgrade. Quartermaster ships ~2-3 weeks
after tubemail v1 and will call saved flows programmatically on day
one. The MCP tool surface (`tm_save_flow`, `tm_list_flows`,
`tm_run_flow`, `tm_get_run_log`) must be agreed before the hub-side
persistence lands, so a Quartermaster-side call doesn't force a
rewrite. Coordination is a 1-hour design conversation + a shared
schema document, not a code change — but it blocks the flow-shell
line item in the effort breakdown until resolved.

Shape sketch (to validate with Quartermaster):

```python
# Hub-side MCP tools
tm_save_flow(name: str, body: str, meta: dict | None = None) -> {name, saved_at}
tm_list_flows() -> [{name, saved_at, last_run_at | None}]
tm_run_flow(name: str, worker: str, meta: dict | None = None)
    -> {run_id, queued_at, first_event_id}
tm_get_run_log(run_id: str) -> [{event_id, ts, kind, content}]
```

A flow in v1 is a single `{worker, message}` step, not a chain.
Chains can layer on in v1.1 — v1 ships the shape that makes chaining
additive (each call targets one worker; a chain is N calls with a
parent `run_id`).

## Correction 1 — SSE reuse claim is wrong; two SSE streams are needed

The design doc says (Constraints): *roster + event timelines stream over
the hub's existing SSE endpoint (reused, not new)*. That is incorrect.

The existing SSE endpoint is `/tubemail/{worker}/stream` at
`src/tubemail_hub/bridge/http.py:97` — a **per-worker, forwarder-facing**
stream that delivers inbound events *to* one worker's forwarder (so that
forwarder can put them on the worker's channel plugin). It is not a
hub-wide "show me all activity" stream the frontend can consume.

**Fix:** add a new frontend-facing SSE endpoint, e.g.
`GET /api/events/stream`, that emits a merged stream of all worker
events across the hub. Implementation: extend `BridgeEngine` with a
`subscribe_all()` async iterator that fans out every `_fan_out` call
(currently per-worker at `engine.py:321`) to this shared subscriber set.

Keep the existing per-worker stream untouched — forwarders still use it.

## Correction 2 — Pty bridge lives on the hub (endpoint), manager already has the pty

The design doc (Open Question 3) left endpoint ownership as "hub vs
manager, TBD from spike." Decide: hub owns the **HTTP/WS endpoint** the
browser connects to; the **pty master itself lives in the manager
process and already exists**.

Verified by reading `channel/src/tubemail/manager.py:179` — the
manager already does `pty.fork()` and holds the master FD. It already
streams bytes into `self._screen_buf` for `tm_screenshot` (line 187)
and writes bytes to the pty via `send_bytes()` (line 216). What's
missing is a **streaming mode** that copies bytes to an SSE channel
as they arrive, rather than just populating the rolling buffer.

This reduces the forwarder/manager change surface to additive work
on an existing pty reader — not a new pty multiplexer as a first-pass
review might assume.

**Architecture:**

- Browser opens `wss://.../ws/pty/<worker>?ticket=<t>`.
- Hub looks up the worker's forwarder, opens (or reuses) a per-worker
  `pty_bridge` session on its internal map.
- Hub sends a `pty_attach` SSE message to the forwarder (new event
  kind on the existing SSE back-channel).
- Forwarder reads pty bytes and POSTs them as batches (e.g. every 16
  ms of accumulated output or every 4 KB, whichever first) to a new
  endpoint `POST /tubemail/<worker>/pty-out`. The hub fans those bytes
  to every attached browser WS.
- Browser keystrokes come in on its WS, hub pushes them as a
  `pty_data` (direction=in) SSE message to the forwarder, forwarder
  writes them to the pty.
- Resize (TIOCSWINSZ) is a separate SSE message kind: `pty_resize`
  with `{cols, rows}`.
- On close (last browser WS goes away for that worker), hub sends
  `pty_detach` to the forwarder; forwarder drops its pty reader.

**Single-subscriber eviction interaction (reviewer catch).** The
existing `subscribe()` at `engine.py:329` evicts duplicate subscribers
— by design, to prevent fan-out to two forwarder processes claiming
the same worker name. Pty control events piggybacking on this channel
inherits that property: only one manager process can be attached at a
time, which matches physical reality (one pty per worker). The
downside: if the manager's forwarder SSE flaps (network blip, hub
restart), the old stream is evicted and the new one reattaches. A few
seconds of browser keystrokes queued during that window are lost.
v1 accepts this; the browser shows "reconnecting…" and the operator
retypes. If the flap rate proves high in dogfood, solve by having the
hub queue `pty_data` SSE messages per-worker with a short (N-second)
retention window, replayed to the new subscriber on attach. Defer
unless needed.

**Framing on the WS:** binary messages for stdout/stdin bytes;
text-frame JSON for control messages (resize, ping). Simpler than
multiplexing everything into one JSON envelope.

**Latency budget:** each keystroke round-trip is browser → hub → SSE
stream → forwarder → pty → response → POST → hub → browser. Two
network hops per direction. On localhost this is <5 ms; across a LAN,
<30 ms. Acceptable for interactive typing.

## Correction 3 — Ticket-exchange auth concrete shape

Already well-spec'd; filling in engineering specifics:

```python
# src/tubemail_hub/bridge/tickets.py  (new)

@dataclass
class Ticket:
    token: str
    worker: str
    expires_at: float

class TicketStore:
    def __init__(self):
        self._tickets: dict[str, Ticket] = {}
        self._lock = asyncio.Lock()

    async def issue(self, worker: str, ttl_s: float = 30.0) -> str:
        async with self._lock:
            token = secrets.token_urlsafe(32)
            self._tickets[token] = Ticket(
                token=token, worker=worker,
                expires_at=time.monotonic() + ttl_s,
            )
            return token

    async def consume(self, token: str, worker: str) -> bool:
        async with self._lock:
            t = self._tickets.pop(token, None)
            if t is None or t.worker != worker:
                return False
            if time.monotonic() > t.expires_at:
                return False
            return True

    async def sweep(self) -> int:
        async with self._lock:
            now = time.monotonic()
            stale = [k for k, v in self._tickets.items() if v.expires_at < now]
            for k in stale:
                del self._tickets[k]
            return len(stale)
```

Background sweep task started in the app's lifespan:
```python
@asynccontextmanager
async def lifespan(app):
    task = asyncio.create_task(_sweep_loop(app.state.tickets))
    try:
        yield
    finally:
        task.cancel()

async def _sweep_loop(store: TicketStore):
    while True:
        await asyncio.sleep(60)
        await store.sweep()
```

`POST /api/pty-ticket` is bearer-authed via the same `auth_dep` used
by the forwarder routes. Rate-limit: reject if a bearer has issued
>10 tickets in the last 60 s — in-memory per-bearer token bucket,
good enough for a single-operator tool, easy to upgrade later.

Single-use is atomic: `consume()` does `pop` + check, one critical
section, no `used` flag.

**WebSocket hardening beyond the ticket (reviewer catches).** Ticket
alone does not close two real attack surfaces; the WS handler MUST
also enforce:

1. **Origin whitelist.** Reject WS upgrades whose `Origin` header is
   not in the allowlist (defaults: `http://localhost:8004`,
   `https://localhost:8004`, configurable via `TUBEMAIL_ALLOWED_ORIGINS`
   env var as a comma-separated list). This blocks a malicious page
   the operator visits from opening `new WebSocket()` to the hub even
   if the bearer or a valid ticket leaked. Cheap; one header check.
2. **TLS-only for pty traffic.** If the hub is serving over HTTP (no
   cert in `/data/server.crt`), reject `/ws/pty/*` upgrades with 426
   Upgrade Required and a body of `{"error":"pty requires TLS"}`.
   Keystrokes carry work-order content; plaintext on the wire is a
   keystroke logger. Landing-page documentation points operators to
   the existing self-signed cert generation path.

Both go in the WS upgrade handler, before ticket consume. Rejection
is logged at `warning` (Origin block) or `error` (TLS missing)
level.

## Correction 6 — Engine integration for the new endpoints

Additions to `BridgeEngine`:

- `subscribe_all()` — AsyncIterator producing every `_fan_out` message
  plus a `worker` field, for the frontend SSE endpoint. Implementation:
  add `self._global_subscribers: list[asyncio.Queue]` alongside
  `_outbound_subscribers`. Modify `_fan_out` at `engine.py:321` so that,
  after pushing to per-worker subscribers, it also pushes a copy of the
  message **with `worker=<worker>` injected** to each global subscriber
  (the caller already knows the worker — add the field inside `_fan_out`,
  do not require every callsite to add it). O(1) extra work per event.
- **Also fan out `record_outbound` and `record_permission_response`.**
  Currently `record_outbound` at `engine.py:183-202` creates the event
  but does NOT call `_fan_out`; outbound replies never appear on the
  SSE stream. For forwarder-targeted SSE that's fine (the forwarder
  created the event, it doesn't need to be told about it). For the new
  global subscriber it matters: the frontend won't see "worker replied"
  without it. Fix: add a `self._fan_out(worker, {"event": "outbound",
  "data": ...})` call after `self._persist(worker)` in
  `record_outbound`. Same treatment for `record_permission_response`.
  This is a second engine-correctness patch alongside the silent-drop
  fix — same PR.

- `attach_pty(worker, client_queue)` / `detach_pty(worker, client_queue)` —
  per-worker pty fan-out registry. Separate from `_outbound_subscribers`
  because pty events don't go on the event log (they're volatile).

- `push_pty_output(worker, bytes)` — called from the new forwarder POST;
  fans bytes to all attached pty clients for that worker.

- `pty_attached_count(worker)` — for the "N clients attached" badge.

These live in a new file `src/tubemail_hub/bridge/pty.py` to keep the
main engine focused on the event timeline. `BridgeEngine` composes a
`PtyBridgeRegistry` instance.

New router modules:

- `src/tubemail_hub/bridge/api.py` — `/api/*` JSON endpoints
  (workers list, pty-ticket issue, permission list/resolve).
- `src/tubemail_hub/bridge/events.py` — `/api/events/stream` global SSE.
- `src/tubemail_hub/bridge/ws.py` — `/ws/pty/{worker}` bridge.

All bearer-authed via the existing `auth_dep`; the WS endpoint
additionally validates the ticket.

## Other engineering items the design doc under-spec'd

### E1 spike scope — concrete pass/fail tests

The spike needs deterministic pass/fail criteria for a 3-day timebox:

1. **Render fidelity.** Claude Code TUI shown in xterm.js. Human-readable,
   no color corruption, cursor tracks, alt-screen works (watch a `htop`
   render), resize reflows. *Test:* launch a real worker, SSH-equivalent
   into it via pty, run `claude-tm`, interact for 5 minutes.
2. **Shift+Enter.** Send `\x1b\r`. If Ink treats it as submit, try
   `\x1bOM`, then `\x1b[13;2u` (Kitty). One of these works or the
   keybinding claim degrades to "Alt+Enter" (functionally equivalent
   modifier on many keyboards).
3. **Bracketed paste.** `printf '\e[?2004h'` on pty; verify Ink echoes
   pasted blob as one input event with surrounding `\e[200~...\e[201~`.
   If Ink does not enable, note: our wrapper can unconditionally wrap
   outgoing pastes, which may corrupt input during `cat >file` or
   similar — acceptable degradation.
4. **WS multiplex.** One WS carries stdout + stdin + resize + ping
   without framing ambiguity. *Test:* 10-minute session with heavy
   redraw (vim opening a large file) and 20 Hz keystroke input, no
   dropped bytes, no garbled frames.

If 3 of 4 pass, ship. If 2 of 4, degrade the cap per the kill-criterion.

### Error handling per the no-silent-errors rule

Three places to audit (existing CLAUDE.md rule):

- `TicketStore.consume` returns False rather than raising — log at
  `warning` level with worker + token prefix (first 8 chars) so denied
  ws connects are observable.
- The new `POST /tubemail/<worker>/pty-out` endpoint: if the worker is
  not registered or has no pty bridge open, return 404 (not silent
  drop). Forwarder retries with backoff.
- `subscribe_all()` queue overflow: if a slow frontend subscriber's
  queue fills, drop and close (do NOT silently stall the fan-out).
  Frontend reconnects.

### Observability

Three log points and two metrics. Cheap to add, huge debug payoff:

- Log: ticket issued (worker, expiry).
- Log: ws pty bridge open/close (worker, client id, duration).
- Log: forwarder pty-out POST rejected (worker, reason).
- Metric: `pty_bridges_attached{worker}` gauge.
- Metric: `events_fanned_out_total` counter.
- Metric: `tickets_consumed_total{outcome}` counter (labels:
  `consumed`, `expired`, `wrong_worker`, `not_found`) — security
  signal for bad-ticket rates.
- Metric: `pty_out_latency_seconds` histogram — from pty byte
  available at manager to delivery at browser; exposes "keystrokes
  feel laggy" as a measurable rather than subjective.
- Metric: `global_subscribers_evicted_total` counter — tracks
  slow-frontend drops from the new global SSE fan-out, so the
  silent-drop-fix stays audited, not just asserted.
- Add per-IP rate-limit metric for `/ws/pty/*` upgrade attempts
  (cap 30/minute/IP). Addresses ticket-scanning attacks; cheap
  middleware.

These go in `bridge/engine.py` via `logging.getLogger("tubemail.hub")`.
No new observability stack needed.

- `tests/test_events_stream.py` — two fake subscribers, emit an event,

## Reviewer Concerns (persisted per office-hours template)

None that block implementation. The plan is coherent and the
corrections above close the last implementation-spec gaps. If any of
these surface during the spike, revisit:

1. The forwarder/manager change is substantive. If the manager
   process turns out to be harder to modify than expected (claude-tm
   is a relatively young wrapper), budget slips by 2–3 days. Mitigation:
   prototype the manager-side pty reader before committing v1 timeline.
2. Bracketed-paste mode in Ink may be version-dependent. If Claude
   Code upgrades and the behavior changes mid-build, v1's paste
   behavior may need a flag. Track the Ink input source version.
3. Browser-side clipboard API on HTTPS-only contexts: v1 ships over
   HTTPS with the hub's self-signed cert, which most browsers treat as
   "not secure" and gate the clipboard API from. Either accept
   Ctrl+Shift+C as the primary shortcut (standard-xterm mode) or
   bundle a proper cert in dev. Non-trivial UX decision; document in
   the Design Review (next in the pipeline).
