# DX Review — tubemail web UI (as-built)

Reviewing:
- Design: `jjstack/jesper-main-design-20260425-092030.md` (as-built)
- CEO: `jjstack/ceo-plans/jesper-main-ceo-20260425-092500.md`
- Eng: `jjstack/ceo-plans/jesper-main-eng-20260425-093000.md`

Generated by `/plan-devex-review` on 2026-04-25.
Mode: **DX POLISH** (existing product, focused friction-finding pass).

Status: **DX is solid for the primary persona but has three friction points
that compound — worker-silent UI, recording-streaming silent failure,
and the README/feature mismatch that misleads new evaluators.**

Score: **7/10.**

The product is usable, the UI is responsive, the keybinding profile is
genuinely good, and the operator can do real work. Two and a half points
off come from "the tool that ships sometimes lies about its state" —
specifically: recording is on but capturing nothing; worker shows busy
but silent; manager-silent overlay only appears 4 seconds in.

---

## Persona — assumed (per user's "minimal interruption")

The README, install path, and overall posture point to one developer:

**Solo orchestrator running multiple Claude Code workers on their own machine.**
This is Jesper today, and probably one or two close collaborators in the
ecosystem. Tolerance for setup friction: high (it's their own tool).
Tolerance for "tool lies about state": low (they're debugging their AI
fleet, they need to trust the dashboard).

If a second persona shows up later — e.g., "platform engineer evaluating
tubemail for a team" — most of the DX problems below get *worse*, not
better. The single-operator persona is forgiving of MCP-tool count and
README mismatches; an evaluator is not.

## TTHW — Time To Hello World

Measured from the README:

```
1. echo 'TUBEMAIL_SECRET=change-me' > .env       (~5s)
2. docker compose up -d tubemail-hub             (~30s first time, image build)
3. cd <project>; claude-tm                       (~2s once installed)
4. open http://localhost:8001                    (~2s)
5. paste TUBEMAIL_SECRET into auth gate          (~10s, requires reading)
```

**TTHW: ~50s if Docker is warm and `tubemail` is already pip-installed,
~5 min if Docker needs to pull and the worker package needs install.**

Champion tier (< 2 min) is achievable with one cleanup: `tryDevBootstrap`
skips the auth gate on localhost, so step 5 is free if the bearer is in
the host's env. That already works. The friction is step 5 only when
running cross-machine. For the assumed solo persona, **TTHW is in the
champion tier.** Good.

## DX Pass 1: Getting Started — 8/10

**Strong:**
- Single command setup: `docker compose up`. ✓
- `tryDevBootstrap` skips the auth gate on localhost. ✓
- The auth gate, when it does appear, has a `grep TUBEMAIL_SECRET ~/PycharmProjects/disciplin-run/tubemail/.env`
  hint right in the UI (`App.tsx:AuthGate`). That's good copy-paste-friendly help.
- Default settings work without configuration. ✓

**Friction:**
- The README's quickstart shows the worker side AFTER the hub side. A new
  evaluator opens the URL, sees an empty "no workers" roster, and has to
  go back to the README to figure out how to start a worker. The empty
  state in `Roster.tsx` does say `Launch one from any project directory:
  claude-tm` — that's the right hint, in the right place. So the empty
  state IS the hint. Good. But the README isn't structured to mirror that
  flow.
- `claude-tm` requires `pip install tubemail` first. That's a separate
  install from `docker compose up`. The README mentions both but doesn't
  call out that they're sequential. A new user may try `claude-tm` before
  the worker package is installed and get a "command not found." Half a
  point off for that.

**Magical moment:**
The current magical moment is "I open the web UI and see all my workers
live, with their states updating in real time." That works. The roster
is what it should be — a live thing, not a refresh-button thing.

**Recommendation (no new features per user):** restructure the README's
Quickstart so the *user-visible flow* (start hub → open URL → start a
worker → see it appear) maps 1:1 with the README sections. The current
order is fine but could be tightened.

## DX Pass 2: API/CLI/SDK Design (MCP Tool Surface) — 6/10

This is the section where the README/reality gap hurts most.

The README says:

> TubeMail ships the send/receive/restart primitives, nothing more.

The actual MCP tool count is 28. List from `tools/workers.py` and
`tools/flows.py`:

```
tm_list_workers, tm_send, tm_receive, tm_status, tm_my_inbox,
tm_wait_for_activity, tm_pending_permissions, tm_respond_permission,
tm_interrupt, tm_restart, tm_stop, tm_purge_worker, tm_keystroke,
tm_update_manager, tm_clear_and_send, tm_reconnect_mcp, tm_health,
tm_screenshot, tm_recording_toggle, tm_recording_status, tm_get_recording,
tm_save_flow, tm_run_flow, tm_list_flows, tm_delete_flow, tm_finish_run,
tm_get_run_log, get_instructions, refresh_tools
```

A new orchestrator opening the MCP surface sees 28 tools. The README
promised 3-ish ("send/receive/restart"). That's a credibility gap. An
evaluator either:

1. Concludes the README is out of date (correct) and adjusts.
2. Concludes the tool surface is over-built relative to the pitched
   minimalism (also fair).
3. Doesn't notice the mismatch because the tool docstrings are good.

The docstrings are good. Each tool has 3-10 lines of clear `@mcp.tool`
docstring with usage examples (`workers.py`). That's where most of the
DX value lives. Good naming (`tm_send`, `tm_receive`, `tm_status`),
good consistency (every tool starts with `tm_`), good defaults (most
take a worker name and reasonable everything else).

**Score 6 because:**
- Tool naming and docstrings are 8/10.
- Tool surface size mis-pitched is 3/10 — the README needs to update.
- Net: 6.

**Fix without new features:** README update (one paragraph) explaining
that tubemail ships transport primitives PLUS an operator surface that
exposes them through a web UI and richer MCP tool set. The existing
"What this is not" section ("not an orchestrator, not a replacement
for native tools") is still true at the policy level. Keep that.

This is also what the CEO review flagged as recommendation #1.

## DX Pass 3: Error Messages & "Tool lies about state" — 5/10

This is the lowest-scored pass and the one with the most concrete
DX impact.

### Trace 1: Recording is on, capturing nothing

User toggles recording on for `architrix-tm`. Hub responds:
```json
{"ok": true, "enabled": true, "active_file": "20260425T155846-144203Z.cast"}
```

User waits, sends commands, comes back. Recording status:
```json
{"enabled": true, "active_file": "20260425T155846-144203Z.cast", "size_bytes": 113}
```

113 bytes is just the asciinema header. No frames captured. The UI does
not surface this. The user only finds out by inspecting the file size
or running `tm_get_recording` and seeing zero frames.

**What the UI should say:** "Recording is on for architrix-tm but no
output has been captured in the last [N] minutes. Possible cause: manager
isn't streaming pty bytes (older manager? roll it?). Roll manager."

This is the single biggest DX failure in the as-built state. Recording
silently failing is worse than recording being unavailable.

### Trace 2: Worker shows busy for hours/days

The 2026-04-25 investigation found `jjstack-tm` was busy for two days
because the hub's status_state had no decay. Fixed with BUSY_DECAY_S.
But the underlying DX issue remains: when a worker is busy for 5
minutes, it's working. When it's busy for 5 hours, something is wrong.
The current UI renders both the same (amber pill, time counter).

**What the UI should say:** at busy > 1 hour, the badge changes color
or the counter renders bold. A subtle "this is unusually long" cue.

### Trace 3: Manager-silent overlay timing

The terminal pane shows "Connecting to architrix-tm..." for 4 seconds,
then drops to "Worker silent" with a Roll-manager card if no bytes
arrive. 4 seconds is a long blank screen. The card itself is great —
specific, actionable, has a button. The wait before it appears is the
gap.

**Possible fix:** show the "Connecting..." message for 1.5s, then
escalate to "Still waiting..." with a "tap to see options" link.
Mid-stage messaging shows progress, not a void.

## DX Pass 4: Documentation & Learning — 7/10

**Strong:**
- The README is well-structured for the "what is this" question.
- Architecture diagram is in the README.
- Each MCP tool has rich inline docstrings (operators discover this when
  loading the tool).
- `get_instructions` MCP tool returns the SERVER_INSTRUCTIONS — orchestrators
  can re-prime themselves on usage without leaving Claude.

**Friction:**
- The README's recording feature isn't documented at all. A user enabling
  it via the Settings page or `tm_recording_toggle` won't find an explanation
  of what `.cast` vs `.frames.jsonl` means, or how to read either.
- The Settings page itself has zero contextual help. Three knobs, no
  descriptions of what they do. The recording paragraph above the knobs
  is the only documentation.

**Easy fix:** add a "Recording" section to the README. ~20 lines covering:
what it captures, where it lives (`/data/tubemail/recordings/<worker>/`),
how to read it (`asciinema play foo.cast` or `tm_get_recording`), how
rotation/GC works.

## DX Pass 5: Upgrade & Migration Path — 8/10

Not heavily tested in the as-built state but the architecture is sound:
- `update_manager` MCP tool re-execs the manager process to pick up
  updated source. The bash wrapper handles the `--continue` flag so
  conversations survive.
- The web UI has a "Roll manager" button that does the same.
- No breaking schema changes have happened since the initial commit.

**Friction (theoretical):** when the WorkerState schema changes (e.g.,
adding `recording_enabled` and `context_pct`), older state files on disk
need to load. Pydantic's `model_validate` ignores extra fields and
fills missing defaults, so this works for additive changes. A subtractive
or rename change would break state files; no migration path is in place.

This is a watch-the-slope concern, not a current bug.

## DX Pass 6: Developer Environment & Tooling — 8/10

**Strong:**
- Live-reload setup is excellent (the very feature that triggered the
  mcp-server skill update). `./src:/app/src:ro` mount + uvicorn `--reload`
  means Python edits land in seconds.
- Frontend hot-reload via `npm run build` writes to `frontend/dist` which
  is bind-mounted into the container. Not sub-second, but fast enough.
- `pytest` works out of the box for the hub and the channel.
- The `claude-tm` bash wrapper is a small, well-named script. Reading it
  is faster than reading docs.

**Friction:**
- Frontend dev requires the operator to know to run `npm run build` in
  the host's `frontend/` directory after edits. Vite watch mode would
  remove that step but isn't wired up.
- No way to dev-mode the channel plugin from a worker without restarting
  claude. `tm_update_manager` re-execs the manager but not the channel.
  Acceptable — the channel rarely changes.

## DX Pass 8: DX Measurement & Feedback — 5/10

**What exists:**
- `/health` endpoint returns KPI-shaped JSON (workers_online, pending_permissions, etc.).
- The MCP `tm_health` tool reports per-worker process stats.
- Recording captures runs for after-the-fact debugging.
- The hub logs structured events in JSON-ish text format.

**What's missing:**
- No TTHW measurement.
- No "did the operator close all their non-web terminals" signal (which
  was a v1 success criterion!). The criterion is observed informally;
  not measured.
- No DX feedback loop within the UI itself ("how's it going" prompt,
  bug-report shortcut, etc.). The persona is one user, so this is
  forgivable. If the persona expands, this needs to.

The success criteria from the as-built doc include "Close every non-web
terminal window on the desktop and still do a full day of orchestration."
The doc says "Not formally measured. Operator reports doing this." That's
the right honesty bar. Filing as a watch-item, not a fix.

## Empathy narrative — the as-built solo-orchestrator experience

T+0:00 — Operator opens laptop after lunch. Browser tab still open from morning.
The tubemail UI shows the roster. 14 workers, mostly green-idle, one yellow-busy
on jjstack-tm with "busy 47s". They scan to see who's working. They click
into iris-qa-tm.

T+0:15 — Terminal pane mounts. The "Connecting to iris-qa-tm..." overlay
shows. After ~1s, bytes arrive, the overlay clears, claude's TUI renders.
Smooth. Operator types a quick `tm_screenshot` request via MCP from
another window.

T+1:30 — Operator wants to record actuatrix-tm before sending it a complex
work order. Goes to Settings. Three knobs. Toggles "Record by default" off
(don't want recording on every worker), then opens the Workers tab and
clicks the rec circle next to actuatrix-tm. Circle goes red. Returns to
the actuatrix terminal pane. Types the work order.

T+5:00 — Comes back, wants to read the recording. Opens MCP tool
`tm_get_recording(worker="actuatrix-tm")`. Returns 0 frames.

> "Wait, what?"

Checks `tm_recording_status`. Says enabled=true, active_file is set,
size_bytes=113. They check the file on disk: just the header. They reload
the page. Same. They turn recording off, on. Same.

This is where DX falls off. There's no signal from the UI that the
recording is in a known-broken state. The Settings page doesn't say
"Recording is on for 3 workers but only 1 is producing data." The
roster doesn't differentiate "recording active and capturing" from
"recording active but silent." The user has to dig into hub logs to
discover the SSE eviction loop.

T+10:00 — They give up on recording for actuatrix-tm and just watch the
terminal pane in real time, like they would have without the feature.
The feature's value prop is undelivered.

This narrative is the strongest argument for the CEO review's
recommendation: fix the recording streaming bug as the next priority.
The DX impact compounds — the user enabled the feature, paid the
ongoing cost (file rotation, settings management), and got nothing.
