## Problem Statement

Today tubemail is a pure MCP transport. The only way to observe or drive it is
from inside an orchestrator session calling `tm_list_workers`, `tm_send`,
`tm_status`, `tm_pending_permissions`, `tm_respond_permission`, etc. The user
(Jesper) has N worker sessions open, each in its own terminal tab, and the
human operator's workflow is a forced tmux-dance between them:

- Approve permissions by walking to the tab with the prompt, pressing Enter.
- Read a reply by staring at a scrollback buffer that rolls away under new
  output.
- Hand off messages by copy-pasting between two terminals.
- Restart a worker by locating its terminal, `/exit`, re-launching.

The proposal: a web UI served on port 8004 alongside `/mcp`, exposing the same
capabilities as the MCP tools — plus true pty-bridged terminal panes per
worker so the human can finally stop living in individual terminal windows.

## What Makes This Cool

The signature feature is the **Integrated Worker Terminal**. Not a screenshot,
not a log tail — a full xterm.js in the browser with a WebSocket pty bridge to
each worker's manager. The differentiator is **keybindings that feel like a
desktop app rather than a terminal emulator**:

- **Shift+Enter inserts a hard newline** that Claude Code's Ink input actually
  reads. The exact byte sequence is spike-dependent (candidates:
  `\x1b\r`, `\x1bOM`, Kitty `\x1b[13;2u`); the spike names the winner.
  Finally you can paste three-paragraph work orders without juggling
  backslash-escapes.
- **Ctrl+C does OS copy when there's a selection, SIGINT when there isn't** —
  the way every other app works. Implementation rides on two browser quirks:
  (1) the async Clipboard API requires a secure context on non-localhost, so
  plain-HTTP cross-machine deploys fall back to standard-xterm Ctrl+Shift+C;
  (2) Linux primary-selection vs. clipboard semantics vary by browser. The
  spike documents the supported matrix.
- **Ctrl+V pastes as a bracketed-paste block** so Claude gets one input, not
  100 keystroke events. This requires Ink to have `ESC[?2004h` active at the
  moment of paste. The spike verifies this; if Ink does not enable
  bracketed-paste mode, the client sends raw bytes and the "one input" claim
  is weaker.
- **Per-window zoom** (Ctrl+=, Ctrl+-, Ctrl+0) persisted in `localStorage`
  keyed on worker name (not restart-epoch), so a restarted `iris-qa-tm`
  keeps the operator's font preference — a long Gherkin review in 18pt, a
  quick health ping in 12pt.

Pop-out to a real browser window (tile four workers across a 4K display) is
the sibling window-management piece of this capability; mechanics are in
Open Question 5 rather than in the keybinding list.

The "whoa" moment is the first time you send a two-screen work order to a
worker via Shift+Enter without once reaching for the backslash. The risk, to
be honest about it: several of those keybinding promises are contingent on
the xterm + Ink spike. If the spike is brutal, the feature ships with
degraded keybindings and that's still a win over iTerm — but less of one.

## North star

The local web UI is a **predecessor** for broader Claude-workload web
interfaces — terminals, web-terminals, Slack notifiers, future
modalities. Many ways to access the work; the web UI ships first.

v1 implications:
- Component boundaries stay reusable. The roster, inbox, terminal pane,
  and state-badge components should be portable to a future shell
  (e.g. "generic Claude-workload cockpit") with minimal rework.
- Don't abstract prematurely (E4 from the CEO review stays rejected).
  Ship tubemail-specific surfaces; generalise later when a second user
  of the shell exists.
- Auth model stays single-operator for v1 (premise 5 holds).
  Multi-operator is a separate future capability, not a v1 foundation
  decision.
- Long-term, workers may go headless — no terminal at all, pure
  programmatic processes managed by the hub. v1 does not foreclose
  this: the pty bridge is an additive capability on top of a worker
  that already runs; when a worker has no pty, the terminal tab simply
  hides itself for that worker.

## Constraints

- **Ecosystem format:** the `specs/product.json` must conform to the leanspecs
  hierarchy (Capability → Feature → Behavior) so leanspecs can ingest it as
  the canonical maintainer.
- **Port:** reuse 8004 (static mount alongside `/mcp`), no new service.
- **Auth:** reuse `TUBEMAIL_SECRET` bearer — no second auth system.
- **Frontend stack:** React + Vite + TypeScript — matches leanspecs and
  iris-qa, enables shared `@disciplin-run/shared-ui` components.
- **Shipped capability dogfood:** the hub bug that started this session
  (`status_state` never returning `busy`) is fixed; the UI must surface the
  new `busy` state visibly or the fix is invisible.
- **Two data planes, one source of truth:** roster + event timelines stream
  over the hub's existing SSE endpoint (reused, not new). The Integrated
  Terminal adds one new endpoint — a WebSocket pty bridge per worker —
  because SSE is one-way and a terminal needs full duplex. The hub's event
  log remains the single source of truth; SSE and WS are two views into
  it, not two truths.

## Worker State Machine (reference)

Referenced throughout this doc. After the `status_state()` fix shipped this
session:

*Terminology note:* "multiplex" appears in two senses in this doc —
(a) one WebSocket carrying read + write + resize frames for one terminal,
and (b) the manager fanning one pty's output across N attached clients (and
interleaving their inputs back into the pty). Both are live in v1 — they
are not the same mechanism.

The hub's `status_state()` returns one of four values. The UI computes an
additional fifth value (`offline`) locally from SSE connection data — the
hub does not return it. Both are shown uniformly in the roster.

| State | Source | When | Signal to operator |
|---|---|---|---|
| `unknown` | hub | Worker never registered. | No row in roster. |
| `idle` | hub | No events yet, or trailing event is `outbound` / `permission_response`. | Green badge. |
| `busy` | hub | Trailing event is `inbound` (orchestrator handed work, no reply yet). | Amber badge + time-since-inbound counter. |
| `waiting_permission` | hub | `pending_permissions` non-empty (beats `busy`). | Purple badge + count. |
| `offline` | UI-computed | Derived in the UI from SSE connection loss + the hub-reported `exited_cleanly` flag + last-seen timestamp. Not a `status_state()` return value. | Red (unclean) / grey (clean). |

`time-since-inbound` = `now() − ts(most_recent_inbound_event)` while state is
`busy`. Resets to hidden when state transitions to `idle` or
`waiting_permission`.

## Premises

Surfaced adversarially during brainstorm. Each is stated plainly so the reader
can disagree.

1. **The real pain is permission fan-out, not visualization.** The worst part
   of the current workflow is having to walk to N terminal tabs to press `y`
   when each worker blocks on a Bash approval. Any UI that doesn't solve this
   cleanly is decorative.

2. **The second-worst pain is reply latency uncertainty.** Jesper just spent a
   full session debugging "did iris-qa-tm actually reply" — the answer was
   "yes, 40 s after you gave up." A UI that shows `state=busy` prominently,
   with time-since-inbound counted up visibly, removes that entire failure
   class.

3. **A browser terminal is a valid substitute for a native terminal, IF the
   keybinding story is right.** If Shift+Enter doesn't work or Ctrl+C
   surprises people, they'll go back to iTerm and the UI has failed. This is
   the premise most likely to break — it's worth prototyping xterm.js +
   Claude-Code-Ink compatibility first, before committing to the rest.

4. **"Orchestration Library" (saved flows) is YAGNI in v1.** The only people
   who'd use saved flows are Jesper and Quartermaster. Jesper is fine with
   text templates in a markdown file; Quartermaster will send programmatically.
   Defer until a second user exists.

5. **The UI is for one operator at a time.** Multi-user collaboration (per-seat
   auth, audit-by-user) is a future-tax. V1 is "Jesper runs the hub; tab open
   on the laptop."

## Approaches Considered

Three genuinely different ways to slice the 10-capability proposal.

### Approach A: "Full suite, big swing" (as proposed)

Ship all 10 capabilities: Worker Roster, Timeline Viewer, Message Composer,
Permission Inbox, Integrated Terminals, Process Control, Health dashboard,
Orchestration Library, Admin/Auth, Tech Specs/Design System.

- **Effort:** XL (6–10 weeks frontend-heavy)
- **Risk:** Medium — every feature is implementable, but the surface area is
  large and it competes with every other ecosystem project for Jesper's
  attention.
- **Pros:** Completeness; matches the leanspecs/iris-qa UI footprint so the
  ecosystem feels uniform; lots of demo surface.
- **Cons:** Most of the surface (Message Composer, Timeline Viewer, Health
  KPIs, Orchestration Library) duplicates what a terminal already does. YAGNI
  risk is high. Momentum-killing scope.
- **Reuses:** leanspecs/iris-qa frontend patterns; `@disciplin-run/shared-ui`;
  hub SSE stream; existing MCP tool surface.

### Approach B: "Terminal-first minimal" (RECOMMENDED)

Cut v1 to the three capabilities that actually replace the tmux-dance:

1. **Worker Roster** — live list, state badges per the state machine above
   (now including `busy`), project grouping, time-since-inbound counter on
   busy rows. Click-through to a worker pane.
2. **Permission Inbox** — one list of all pending permissions across all
   workers, keyboard-shortcut allow/deny, bulk by tool-name (one-shot over
   the current inbox — persistent "always allow" rules are out of scope).
3. **Integrated Worker Terminal** — xterm.js pty bridge, keybinding profile
   (Shift+Enter, Ctrl+C/V), zoom, pop-out window.

Everything else (Message Composer, Timeline Viewer, Process Control, Health
dashboard, Orchestration Library, Admin/Auth UI) is deferred. A real terminal
pane subsumes most of them — you already have a shell + claude-code UI;
composing messages means typing into it.

- **Effort:** L (3–4 weeks for one engineer focused). First draft said 2–3
  weeks; that was optimistic given a load-bearing spike, ws-auth not yet
  chosen, and bracketed-paste behaviour unverified. Plan with the longer
  number.
- **Risk:** Med. Three load-bearing claims all ride on the xterm spike:
  (a) Ink renders cleanly inside xterm.js, (b) Ink enables bracketed-paste
  mode so Ctrl+V behaves, (c) a workable Shift+Enter byte sequence exists.
  If (a) fails, the whole capability dies and Approach C becomes the
  recommendation.
- **Pros:** Addresses the two ranked pains (premises 1 and 2) with the
  smallest possible surface. Ships fast. The terminal pane is the headline
  feature and everything is in service of it.
- **Cons:** No "pretty" timeline visualization — if the demo audience expects
  a dashboard, this feels bare. No saved flows. No health graphs. Several
  keyboard-UX claims (Ctrl+C selection-aware copy, Ctrl+V bracketed paste)
  are contingent on browser + Ink behaviour; fallback is "works
  standard-xterm-style" which is still a usability win but less of a "whoa."
- **Reuses:** Hub SSE for roster; `tm_pending_permissions` and
  `tm_respond_permission` for inbox; the manager already owns the pty, only a
  WebSocket bridge is new (new code, not new infra).

### Approach C: "Headless-first, thin status page"

Don't build a full UI. Improve the MCP tool ergonomics so the orchestrator
itself is the UI, and ship a single-page `/status` view on the hub that shows
the worker roster + pending permissions. No terminals, no composer, no
history.

- **Effort:** S (3–5 days)
- **Risk:** Low
- **Pros:** Tiniest possible investment; frees time for the rest of the
  ecosystem. Doesn't commit to a browser-as-desktop-app premise that might
  not pan out.
- **Cons:** Doesn't address the terminal-dance pain Jesper explicitly called
  out. The "whoa" feature is absent. Permission fan-out is still a pain
  because `/mcp` approval still has to happen in the worker terminal.
- **Reuses:** Everything. Almost all of the value comes from what already
  exists.

## Recommended Approach

**Approach B — Terminal-first minimal.**

Rationale:
- It's a direct response to the ranked pains (permissions, latency
  uncertainty, terminal-juggling), not speculative feature surface.
- The Integrated Worker Terminal is the unique differentiator. Every other
  capability is table stakes; the terminal is the reason this UI exists.
- Approaches A and C both fail on specifics: A over-ships because of
  ecosystem-symmetry pattern-matching (every other MCP has a full UI, so
  tubemail should too), C under-ships by not solving the permission
  fan-out pain.
- B leaves option value. If the terminal pane works and Jesper uses it, the
  rest of Approach A becomes easy incremental adds — Timeline Viewer,
  Message Composer, Health dashboard all layer on top of an established
  UI shell. If the terminal doesn't work (xterm/Ink incompatibilities), B
  has contained the damage to 2 weeks, not 8.

**Explicit kill list for v1:**
- Cut Message Composer (use the terminal).
- Cut Worker Timeline Viewer (the terminal has scrollback + `tm_receive` covers
  programmatic needs).
- Cut Process Control Console (buttons above the terminal chrome handle it).
- Cut Health & Observability dashboard (surface CPU/mem inline in the roster
  row; no separate page).
- Cut Orchestration Library (YAGNI — premise 4).
- Cut Admin & Auth UI (env vars are fine; cert mgmt is one-time infra).
- Keep Technical Specifications + Design System caps as spec metadata only
  (ADRs + conventions). They are not features to build; they frame the
  other caps.

Keep these as **v1.5 / v2 sketches** in the product.json under a
`kano_level: 5+` tier so they're visible as intended future work without
blocking v1.

**Changes to the roster cap (not a new capability):**
- **Time-since-inbound counter rendered inside the Worker Roster row** — one
  span of text per busy row, format `busy 2m14s`. Directly addresses
  premise 2. Not a separate feature, not a dashboard; just a cell value in
  the roster table that derives from the state machine.

**Event-log search** — was promoted in the first draft, removed here. It's
effectively a grep-flavoured Timeline Viewer, and keeping it while killing the
Timeline is inconsistent. Defer to v1.5 unless incident forensics becomes an
explicit pain point.

**Permission Inbox bulk-action definition** — "bulk by tool-name" means
one-shot: approve/deny all pending `Bash` prompts *currently* in the inbox.
Persistent rules ("always allow Bash on iris-qa-tm") are out of scope for v1
— they would need a policy store and audit trail.

## Open Questions

These must be resolved before v1 starts, not during it. Some are spike-gated.

1. **xterm.js + Ink TUI compatibility — accepted risk, no pre-build spike.**
   (Decision 2026-04-24: Q1 resolved — no 3-day spike.) The build
   proceeds straight to v1; xterm/Ink compatibility is validated
   *during* the terminal cap implementation rather than gated before
   it. The exact Shift+Enter byte sequence is determined during build
   (candidates: `\x1b\r`, `\x1bOM`, `\x1b[13;2u` Kitty-style). If
   compatibility genuinely fails, the terminal cap degrades per the
   capability-level success criterion; roster + inbox still ship.
2. **Does Ink enable bracketed-paste mode (`ESC[?2004h`)?** If yes, the
   client just sends the paste wrapped in `\x1b[200~...\x1b[201~`. If no,
   the client sends raw bytes and the whole "one input, not 100
   keystrokes" property is lost. Check during the spike.
3. **Pty bridge mechanics.** The hub today exposes `tm_screenshot` (read
   pty) and `tm_keystroke` (write pty), both of which relay to the
   manager process that actually owns the pty. A terminal needs
   low-latency full duplex, which the MCP round-trip does not deliver.
   Likely a new WebSocket endpoint — probably on the hub, proxying to
   the manager over the existing SSE back-channel, or directly on the
   manager if that is cleaner. Spike outputs: endpoint ownership
   (hub vs manager), framing, and whether one socket can multiplex
   resize + keystroke + read.
4. **WebSocket authentication.** Browsers cannot set custom headers on
   `new WebSocket()`. Three options, pick one before v1:
   (a) token in query string — simplest, but leaks in hub logs and
   proxy logs, rotates on every reload; (b) Sec-WebSocket-Protocol
   subprotocol carrying the token — doesn't log-leak but is a minor
   abuse of the header; (c) short-lived ticket over HTTPS. Recommended:
   (c), with this lifecycle:
   - Client calls `POST /api/pty-ticket` with the bearer header; body
     names the target worker.
   - Hub returns a 32-byte random ticket, stored in an in-memory map
     `{ticket → (worker, expiry_ts, used=false)}` with TTL 30 s.
   - Client opens `wss://…/ws/pty/<worker>?ticket=<ticket>`. Hub looks
     up the ticket, checks expiry, and deletes the entry on
     consumption (single atomic op — no `used` flag to track). A
     background task sweeps expired-but-unused tickets once a minute
     so the map does not grow; removal on use is synchronous, removal
     on timeout is swept.
   - Subsequent reconnects (pop-out window, Reconnect button) each
     require a fresh ticket POST. No replay: single-use + TTL.
   - Reconnect storms (e.g., hub flap) don't DOS because ticket POST is
     bearer-authed and cheap; the attack surface is the bearer, not the
     ticket.
5. **Pop-out session sharing.** v1 pick: each pop-out window is its own
   attached client to the same pty. Manager-side multiplex: the pty's
   output fan-outs to every connected WebSocket. Pty *input* from any
   client is written to the pty verbatim; we do not try to lock or
   serialise between clients (see Failure & Recovery — "Two humans
   typing"). Scrollback is per-window (browser-local xterm.js buffer);
   the authoritative history remains the hub-side event log. TIOCSWINSZ
   on resize: the last client to resize wins (see Failure & Recovery —
   "Resize conflict").
6. **SPA fallback route.** Mounting `StaticFiles(html=True)` at `/`
   handles the index but 404s on client-side deep links (e.g.,
   `/workers/iris-qa-tm`). Mount-order pattern:
   1. `app.mount("/mcp", mcp_app)` — specific first.
   2. `app.mount("/api", api_router)` — JSON endpoints.
   3. `app.mount("/events", sse_router)` — existing SSE stream.
   4. `app.mount("/ws", ws_router)` — new WebSocket pty bridge.
   5. `app.mount("/", StaticFiles(directory="frontend/dist", html=True))`
      — SPA last. `html=True` makes `index.html` the fallback for
      unresolved paths, which is what the SPA router needs.
   Verified against the `mcp-server` skill pattern (SKILL.md §"Serving
   a Web UI" / §"Adding extra routes"); the ordering is canonical and
   documented there.
7. **Native window wrapper (Electron/Tauri) as fallback plan.** If the
   browser can't deliver the desktop-app feel (Ctrl+W intercept,
   independent window focus groups, native clipboard without
   user-gesture friction on HTTP), a Tauri wrapper over the same web
   UI is the fallback. Does not change v1 scope; documented here so
   the option exists. Decision point: end of xterm spike.

## Success Criteria

v1 is done when Jesper can, in a single browser tab:
- See every running worker and its current state (idle/busy/waiting_permission).
- Approve a Bash permission prompt from iris-qa-tm in ≤2 keystrokes without
  walking to that worker's terminal.
- Open an integrated terminal to any worker, type a multi-paragraph work
  order using Shift+Enter, hit Enter once to submit, and watch the reply
  stream back.
- Close every non-web terminal window on the desktop and still do a full
  day of orchestration.

Failure modes that count as v1-failure:
- xterm.js corrupts Ink's TUI badly enough that a human can't read it.
- Shift+Enter still requires a platform-specific hack.
- Permission approval UX is no faster than walking to the worker tab.

## LeanSpecs hierarchy sketch

Translating the v1 kept caps into leanspecs Capability → Feature → Behavior
shape so the downstream `/plan-eng-review` and the eventual `spec_create`
calls into leanspecs have a concrete starting point, not just prose.

This is a sketch (1–2 features per cap, 2 behaviors each). The real
`specs/product.json` draft will expand it.

### Cap: Worker Roster Dashboard
- **Gherkin (capability-level):** *Rule: every connected worker MUST appear
  in the roster with its hub-reported `status_state` plus UI-computed
  offline state.*
- **OKR:** Q2-2026 / KR2 (Quality) — "operator can read current state
  without a tool call."
- **Feature: Live state rendering**
  - *Feature Gherkin:* As an operator, I want live worker states so I can
    decide what to do next without polling.
  - Behavior: `render_state_badge` — Given worker X `status_state()==busy`,
    When roster renders, Then show amber badge + time-since-inbound
    counter.
  - Behavior: `derive_offline_locally` — Given SSE disconnect >5 s for
    worker X, When UI refreshes, Then render X as offline (red if not
    exited cleanly, grey if `exited_cleanly==true`).
- **Feature: Click-through to worker detail**
  - Behavior: `open_worker_pane` — Given roster row clicked, When
    navigate, Then render the terminal + permission subpanes for that
    worker.

### Cap: Permission Inbox
- **Gherkin (capability-level):** *Rule: every pending permission across
  all workers MUST be reachable from one place, with allow/deny
  round-tripped through `tm_respond_permission`.*
- **OKR:** Q2-2026 / KR3 (Efficiency) — "operator resolves a pending
  permission in ≤2 keystrokes."
- **Feature: Unified pending list**
  - Behavior: `list_pending_across_workers` — Given N workers with
    pending permissions, When inbox loads, Then all N are shown, grouped
    by worker.
  - Behavior: `keyboard_resolve` — Given a row focused, When operator
    presses Y, Then `tm_respond_permission(…, behavior=allow)` runs and
    the row disappears.
- **Feature: Bulk by tool-name (one-shot)**
  - Behavior: `bulk_allow_by_tool` — Given the inbox has K pending
    `Bash` prompts, When operator triggers bulk-allow on `Bash`, Then
    all K `tm_respond_permission(behavior=allow)` calls run, no
    persistent rule is stored.

### Cap: Integrated Worker Terminal
- **Gherkin (capability-level):** *Rule: every worker with an active
  manager MUST be accessible via a browser-side pty bridge using the
  keybinding profile, with fall-back to xterm defaults if the profile
  cannot be applied.*
- **OKR:** Q2-2026 / KR1 (Quantity) — "operator drives N workers from
  the browser instead of N terminals."
- **Feature: Pty bridge**
  - Behavior: `attach_via_ticket` — Given a valid ticket, When client
    opens `wss:/ws/pty/<worker>?ticket=…`, Then pty read/write/resize
    are multiplexed on that socket.
  - Behavior: `reconnect_blank_scrollback` — Given a ws disconnect,
    When client requests a new ticket and reconnects, Then terminal
    reattaches to the live pty with an empty client-side scrollback.
- **Feature: Desktop-native keybinding profile**
  - Behavior: `shift_enter_hard_newline` — Given focus in the terminal,
    When operator presses Shift+Enter, Then the sequence identified in
    the xterm spike is sent to the pty and Ink reads it as "modifier
    held, do not submit."
  - Behavior: `ctrl_c_selection_aware` — Given a selection exists in
    the terminal, When operator presses Ctrl+C, Then the selection is
    written to the OS clipboard and no SIGINT is sent; given no
    selection, Ctrl+C sends ETX.

### Cap: Saved Messages / Flow Shell
- **Gherkin (capability-level):** *Rule: every saved flow MUST be
  invocable both interactively (operator via the UI) and
  programmatically (Quartermaster via MCP tool), with a shared
  persistent store on the hub.*
- **OKR:** Q2-2026 / KR1 (Quantity) — enables Quartermaster-driven
  fleet operations atop tubemail's transport.
- **Feature: Named flow CRUD**
  - Behavior: `save_flow` — Given a flow body and a name, When saved,
    Then persisted on the hub under `/data/flows/<name>.json` and
    appears in both the UI dropdown and `tm_list_flows` MCP output.
  - Behavior: `run_flow` — Given a saved flow name and a target
    worker, When invoked, Then the flow body is delivered as an
    inbound event to the worker (same path as `tm_send`) and a
    `run_log` is persisted on the hub.
- **Feature: Flow editor (UI)**
  - Behavior: `edit_flow_chain` — Given a flow, When the operator
    opens the editor, Then they can append/reorder/delete steps;
    each step is a `{worker, message}` pair.
  - Behavior: `view_run_log` — Given a past run, When the operator
    opens it, Then the timeline of inbound → reply events per step
    is shown with timestamps.

### Supporting (spec metadata, not build work)
- **Technical Specifications capability:** ADR entries for the pty
  bridge, the ticket-exchange WS auth, the SPA mount order, the
  state-machine extension. No implementation behaviors — these describe
  decisions, not features.
- **Design System capability:** state-color palette, event-kind
  iconography, terminal-window chrome. Conventions, not behaviors.

## Failure & Recovery

The capability shortlist is incomplete without naming how each capability
degrades.

- **Pty bridge disconnect.** Worker restart, manager crash, or network
  drop severs the WebSocket. Two streams to reconcile, kept separate:
  - *Hub event log (inbound/outbound/permission/interrupt events).*
    Persisted in `events.json`. On SSE reconnect, the UI resumes from
    the last seen `event_id` cursor — roster and any timeline panels
    catch up deterministically.
  - *Pty byte stream (what scrolls across the terminal).* Not
    persisted anywhere in v1. On WS reconnect, the terminal reattaches
    to the live pty and its scrollback starts blank. Accepted loss —
    *the hub event log is the authoritative record for what Claude
    said*; the terminal view is live-only and should be treated as a
    window onto the session, not a transcript. Operators wanting to
    read historical replies use the event log (or `tm_receive`), not
    the terminal. If a future version wants replayable pty output,
    the manager would need a ring buffer with a byte-offset cursor.
    Explicitly deferred.
  UX: terminal pane shows a disconnected banner with a single
  "Reconnect" button; click requests a fresh ticket and reattaches.
- **Permission race.** Two browser tabs both have the Permission Inbox
  open; both click allow on the same `request_id`. Resolution: the hub
  already dedupes by `request_id` — `bridge/engine.py:214` checks
  membership before recording and `resolve_permission()` returns
  `ok=False` if the pending entry is already gone. The second tab's
  allow becomes a no-op; the UI shows "already resolved" and
  auto-removes the row.
- **Reply arrives after timeout.** The original bug that started this
  session. UX: the roster row stays `busy` until the reply lands, with
  the time-since-inbound counter ticking up. Orchestrators read the
  counter as "it's still working, don't send again." The inbox never
  silently drops an event.
- **Bearer secret in WebSocket URL.** Not using query-string auth for
  exactly this reason (see Open Question 4). The ticket-exchange pattern
  means the token in the URL is single-use and expires in 30 s, so a
  leaked nginx log is not a credential.
- **Stale frontend after deploy.** SPA cache headers per the
  `mcp-server` skill's guidance at `SKILL.md:566` — `index.html`
  served with `Cache-Control: no-store`, hashed assets cached
  indefinitely. New deploy invalidates the cache without surgery.
- **Hub restart mid-session.** All active WebSockets drop; SSE drops.
  UI shows a hub-level reconnect banner. On reconnect, roster re-fetches;
  timelines resume from last event cursor; terminals need a manual
  reconnect (same Reconnect button as pty-disconnect case).
- **Manager dies.** The manager owns the pty, so killing the manager
  kills the worker — they go down together. The UX is the same as the
  pty-disconnect case above: roster row flips to `offline`, terminal
  banner offers Reconnect, reconnect fails until the manager restarts.
  Operator-level recovery, not UI-level.
- **Resize conflict with multiple clients on one pty.** Two pop-out windows
  disagree about columns×rows. Resolution: the pty size tracks the most
  recent TIOCSWINSZ sent by any client; we do not try to pick a
  "consensus." Each client re-renders on every size change. Acceptable
  jitter; documented so it is not surprising.
- **Two humans typing on the same pty.** The manager multiplexes input
  byte-by-byte, which means simultaneous typing will interleave and
  corrupt whichever session is live. Mitigation for v1: the pop-out
  window shows a small "this pty has N clients attached" badge so the
  operator knows they are sharing a session. No input-locking in v1 —
  this is a single-operator tool (per constraint).

## Distribution Plan

  `SKILL.md:532` — "Serving a Web UI").

  --build` deploys the UI alongside the MCP server.

  install, `./src:/app/src:ro` mount, uvicorn `--reload`). Extend with

  tests only. Adding `vite build` requires a Node.js toolchain step
