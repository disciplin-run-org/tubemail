### Branch C — Name collision in `.mcp.json`

**ACTION**
- claim: The monorepo `.mcp.json` registers `tubemail-channel` as a
  regular stdio MCP server (`{"command": "tubemail", "args": []}`).
  Claude Code, when launched with
  `--dangerously-load-development-channels server:tubemail-channel
   --plugin-dir <channel>` (which is what `claude-tm` does), already
  has `tubemail-channel` registered as a development channel. Two
  registrations under the same name.
- evidence: `cat .mcp.json` (at the disciplin-run repo root) shows the entry.
  `ps -ax | grep tubemail` shows every claude-tm worker has BOTH the
  `--dangerously-load-development-channels server:tubemail-channel` flag
  AND a separate `python ~/.local/bin/tubemail` child (one per worker,
  plus extras for some).
- confidence: verified.

**CONDITION**
- claim: The duplicate-named server, started via `.mcp.json`, exits
  immediately with "TUBEMAIL_SECRET not set — refusing to start"
  because that env var is only set inside the `--dangerously-load-development-channels`
  spawn path. So Claude has one healthy `tubemail-channel` and one
  perpetually-failing duplicate. The `/mcp` dialog rendering, retry
  loop, or status query could plausibly stall on the failing one.
- evidence: `channel/src/tubemail/__main__.py:51-53` prints the refusal
  message and returns 2 when `TUBEMAIL_SECRET` is unset. No env-var
  setup in the regular `.mcp.json` entry.
- confidence: verified for the broken duplicate; hypothesis for it
  being the cause of the keystroke freeze.

### Class boundary

The failure class is **"a write to the wrapped Claude pty that the
operator did not initiate."** Anything in the manager that writes to
master_fd (bytes, SIGWINCH, /command) without the local user driving it
is in this class. The regression test boundary is: exhaustive coverage
that every `os.write(master_fd, …)` and every `TIOCSWINSZ` ioctl in
manager.py has an explicit operator-intent precondition asserted by a
test, and that the auto-accept and rate-limit detectors cannot fire
inside a `/mcp` dialog (e.g., guard them on a "TUI dialog open"
heuristic, or just disable them while a dialog is detected on screen).

### Branch D — Hub eviction-loop degraded all channel plugins (CONFIRMED ROOT)

User-supplied hypothesis after the freeze self-resolved: "the recording
tubemail server was down." Verified.

**ACTION**
- claim: Three workers (`jjstack-tm`, `architrix-tm`, `ollama-tm`) entered
  a hot duplicate-session eviction loop on the hub. Each fresh
  channel-plugin SSE subscribe evicts the previous one, the plugin
  reconnects, gets evicted again — at ~58 events/sec sustained.
- evidence:
  - `docker logs tubemail-tubemail-hub-1 --since 5m 2>&1 | grep -c
     "evicting"` → **17,647** events in 5 minutes (~58/sec).
  - The three offenders are the three workers always paired in the
    `evicting 1 existing subscriber(s)` log lines.
  - The eviction-loop class was already documented in
    `jjstack/ceo-plans/jesper-main-eng-20260425-093000.md` (today's
    eng review): "the channel plugin's SSE subscribe + reconnect
    would catch eviction-loop."
- confidence: **verified.**

**CONDITION**
- claim: While the hub event loop is saturated processing 58/sec of
  eviction work, response latency for *every* hub-talking client
  degrades — including `tubemail-tm`'s channel plugin. The channel
  plugin runs inside Claude as a stdio MCP server; its asyncio loop
  is shared with hub I/O (SSE reconnect, post_outbound, etc.). When
  hub I/O takes long enough, JSON-RPC `tools/list` and follow-on
  status queries from Claude's `/mcp` dialog stall on the same loop.
  Claude's Ink TUI then renders the dialog (because the *first* RPC
  succeeded) but stops processing follow-on key events while waiting
  for the next stdio response from the wedged plugin.
- evidence:
  - `tubemail-tm`'s channel plugin shares one asyncio loop between
    `JsonRpcStdio.run()` (Claude ↔ plugin) and `_pump_hub_events()`
    (plugin ↔ hub) — see `channel/src/tubemail/channel.py:271-282`.
    Hub stalls on the latter starve the former.
  - The freeze self-resolved: the user retried `/mcp` later and it
    worked normally. Consistent with a transient hub-loadhic stall,
    not a code path that's wedged forever.
- confidence: **verified for the eviction-storm load**, hypothesis for
  the exact path (RPC starvation vs. status-query timeout) by which it
  manifests as a frozen dialog. Either way, the dependency chain
  (hub stress → plugin stress → /mcp dialog stress) is verified.

→ Branch D is the **most likely actionable root.** It also explains the
self-resolution (hub keeps grinding through evictions, briefly catches
up, channel plugin services the queued RPC, dialog "thaws").

## STATUS

**DONE_WITH_CONCERNS.** Verified root: the hub's eviction loop for
`jjstack-tm` / `architrix-tm` / `ollama-tm` (~58/sec for at least the
last 5 minutes) was loading the hub event loop heavily enough to
degrade the in-Claude `tubemail-channel` plugin's responsiveness.
Claude's `/mcp` dialog renders, then stalls on subsequent stdio
roundtrips with the plugin. When the hub catches up, the dialog
unfreezes (which is what just happened — three `MCP dialog dismissed`

Not caused by my recent work:

The eviction-loop class itself was flagged in

## REGRESSION TEST CLASS BOUNDARY

Single-incident test (too narrow): "when the hub is doing 58 evictions/sec
for jjstack-tm, /mcp on tubemail-tm responds in <2s."

Class-boundary test (right level): **"the channel plugin's stdio RPC
remains responsive to Claude (`tools/list`, `tools/call`, `ping`) within
a bounded latency budget regardless of hub state — including hub
unreachable, hub slow, and hub returning errors."**

Concretely:
1. Decouple the plugin's stdio RPC loop from its hub I/O. Either:
   (a) give them separate threads/event loops, or
   (b) put hard timeouts on every hub call inside the asyncio loop so
       no single hub stall can monopolize a tick.
2. Add a regression test that stubs the hub to be very slow (e.g.,
   500ms per response, looped) and asserts the channel plugin still
   answers JSON-RPC `tools/list` in <50ms.
3. Add a regression test that stubs the hub to return repeated
   eviction-style 4xx errors and asserts the same RPC latency bound
   plus an exponential-backoff cap on reconnects.

## ALSO ACTIONABLE — fix the eviction loop at the source

Even if the channel plugin is hardened, the eviction storm is itself
a bug. From the existing eng-review CEO plan, the fix is to make the
hub idempotent on duplicate registrations rather than firing
"evict-then-resubscribe-then-evict" every time a forwarder reconnects.
That's outside this incident's scope but has the same actionable owner
and timeline.
