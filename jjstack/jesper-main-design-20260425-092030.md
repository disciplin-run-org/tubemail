## Why this doc exists

The original `jesper-main-design-20260423-215025.md` was the pre-build plan.
Since then, v1 shipped, plus a recording capability that was not in the
original scope, plus three small UX adds. This doc is the post-ship
reconciliation. It exists so the downstream reviews (`/plan-ceo-review`,
`/plan-eng-review`, `/plan-devex-review`, `/plan-design-review`) can
critique what was actually built rather than what was planned.

For each capability the original doc described, this one records:
- whether it shipped,
- where it lives in the code,
- where the implementation diverged from the plan, and why.

The original doc is unchanged on disk. This one supersedes it.

## What shipped — capability-by-capability

### Cap 1: Worker Roster Dashboard — SHIPPED

Lives at `frontend/src/components/Roster.tsx` + `bridge/api.py:74` (`/api/workers`)
+ `bridge/engine.py:list_workers()`.

Matches the plan:
- Live state badges (`idle` / `busy` / `waiting_permission` / `offline` /
  `offline-clean`) computed from `WorkerState.status_state()` plus the
  UI-derived `online` flag (`StateBadge.tsx`).
- Time-since-inbound counter on `busy` rows.
- Project grouping (leanspecs, iris-qa, etc. each become a parent group with
  role-scoped children rendered as `↳ <role>` underneath).
- Click-through opens the per-worker terminal pane in the same view.

Diverged from the plan, noted plainly:
- **Sortable column headers** (added 2026-04-25). Click cycles asc → desc → off
  (back to project grouping). All seven columns sort: Worker, Mgr, Version,
  State, Directory, Ctx, Rec. Plan didn't mention sortability — added because
  the roster grew past ~15 rows in real use and finding a worker became hunt-and-peck.
- **`Ctx` column** (added 2026-04-25). Shows the worker's current
  context-window % parsed from the TUI status bar by the manager and POSTed
  to `/tubemail/<worker>/context-pct`. `—` when the manager hasn't reported
  yet (older managers do not post until rolled). Plan didn't mention context %.
- **`Rec` column** (added with the recording feature). Per-row toggle for
  recording on/off. See Cap 6.
- **Removed: blue SSE dot in column 1** (2026-04-25). The original design
  rendered an 8px SSE-state dot in the leftmost cell. State is already
  expressed via the State badge and Mgr column; the dot was redundant.
- **Status state busy decay** (2026-04-25). Trailing-`inbound` event older
  than `BUSY_DECAY_S = 600s` decays back to `idle`. Without this, a worker
  that handled a work order with code edits but no channel reply stayed
  "busy" forever. Discovered when `jjstack-tm` sat at `busy` for two days
  after silently completing two work orders.

### Cap 2: Permission Inbox — SHIPPED

Lives at `frontend/src/components/PermissionInbox.tsx` + `/api/permissions` +
`/api/permissions/resolve`. Matches the plan: cross-worker pending list,
keyboard allow/deny, group-by-worker. Bulk-by-tool-name shipped as one-shot
(no persistent rules), as scoped.

### Cap 3: Integrated Worker Terminal — SHIPPED

Lives at `frontend/src/components/TerminalPane.tsx` + `bridge/ws.py` (WebSocket
endpoint at `/ws/pty/<worker>?ticket=...`) + the manager's
`_pty_stream_loop` in `channel/src/tubemail/manager.py:_pty_stream_loop`.

Matches the plan in shape:
- xterm.js + FitAddon, ticket-exchange WS auth (Open Question 4 → option (c)),
  one socket multiplexes pty read + write + size echo.
- Keybinding profile: Shift+Enter, Ctrl+C selection-aware, Ctrl+V paste,
  Ctrl+= / Ctrl+- / Ctrl+0 zoom, Ctrl+A select-all, Ctrl+Shift+C / Ctrl+Shift+V
  always-works copy/paste.
- Pop-out window — each pop-out is its own attached client to the same pty,
  manager fans bytes to all clients, last-resize-wins on TIOCSWINSZ.
- Manager owns the pty size; browser conforms (no FitAddon-driven resize).

Diverged:
- **No xterm spike was run** (Open Question 1, deferred-then-resolved). The
  team accepted the risk and validated compatibility during build. Ink
  rendered cleanly enough that no fallback was needed.
- **Bracketed paste** (Open Question 2). Verified Ink does not enable
  `ESC[?2004h`; the client sends raw bytes for paste. Documented in
  `TerminalPane.tsx:writeClipboardToPty`. Lost the "one input, not 100
  keystrokes" property; multi-line paste still works because Ink reads
  `\r` and `\n` reasonably.
- **Popout sizing fix** (added 2026-04-25). Original popout used `width=1000,height=700`
  with a fixed `.terminal-pane { height: calc(100vh - 140px) }` rule designed
  for the embedded case. Net result: 140px of dead space at the bottom of
  the popout window so the prompt was clipped. Fixed via `.popout-host`
  flex-fill class + `resizePopoutToFitPty` that grows the window to match the
  manager's pty grid on first size message.
- **Worker-silent fallback UI**. When no PTY bytes arrive within 4 seconds of
  WS connect, the terminal shows a "Roll manager + reconnect" card. Covers
  the case where the manager is older than the live-terminal feature (started
  before 2026-04-24) and silently ignores `pty_attach` events.
- **Context loss on WS reconnect** (Failure & Recovery item, kept as designed).
  Pty scrollback is per-window; reconnect lands on a blank xterm. Hub event
  log remains the authoritative record.

### Cap 4: Saved Messages / Flow Shell — SHIPPED (against the plan)

Lives at `frontend/src/components/FlowEditor.tsx` + `bridge/flows.py`
(`FlowStore`) + `/api/flows` + the MCP tools `tm_save_flow`, `tm_run_flow`,
`tm_list_flows`, `tm_delete_flow`, `tm_finish_run`, `tm_get_run_log`.

Diverged from the plan:
- The original doc explicitly **deferred this** (premise 4: "saved flows is
  YAGNI in v1"). The premise was overruled during build. Reasoning that
  led to the override is not in the original doc; recorded here so the
  reviews can interrogate it: the orchestrator side wanted a programmatic
  way to invoke named templates without rebuilding them every time, and
  the operator side wanted the same templates accessible from the UI. One
  store, two clients. Cheap once one of them existed.
- Run-log behaviour matches the original sketch in the LeanSpecs hierarchy.

### Cap 5: Process control — SHIPPED as terminal-pane buttons + MCP tools

Plan said "Cut Process Control Console" and "buttons above the terminal
chrome handle it." This is what shipped:
- Buttons in the terminal chrome strip: Roll-manager (RefreshCw icon),
  Pop-out, Reconnect, Close. See `TerminalPane.tsx:terminal-chrome-right`.
- Trash icon on offline rows in the roster (purges the registry entry).
- MCP tools for everything programmatic: `tm_restart`, `tm_stop`,
  `tm_purge_worker`, `tm_keystroke`, `tm_update_manager`, `tm_clear_and_send`,
  `tm_reconnect_mcp`, `tm_health`, `tm_screenshot`. All in `tools/workers.py`.
- No separate "Console" page. Consistent with the plan's intent.

### Cap 6: Recording (NOT IN ORIGINAL PLAN — added as a v1 capability)

This was not on the original capability list. Added because the operator
needed a way to debug a long-running worker session after the fact,
without sitting at the popout terminal in real time. Tees the worker's
PTY output to two parallel files per session so the orchestrator (or a
human) can review the run later.

Files (`src/tubemail_hub/recorder.py`):
- `<data>/recordings/<worker>/<ts>.cast` — asciinema v2, full fidelity, replay
  with `asciinema play`.
- `<data>/recordings/<worker>/<ts>.frames.jsonl` — one ANSI-stripped text
  frame per chunk; what `tm_get_recording` reads. Optimized for grep + time
  slicing.

Knobs (`src/tubemail_hub/config.py` + `/api/settings`):
- Global default `recording_enabled_by_default: bool` — applied to brand-new
  workers on first register.
- Rotation knob `recording_max_bytes_per_file` (default 5 MiB).
- GC cap `recording_keep_files` (default 4 per worker).
- Per-worker override `WorkerState.recording_enabled` — flipped via
  `tm_recording_toggle` or the per-row toggle in the roster.

Surfaces:
- MCP: `tm_recording_toggle`, `tm_recording_status`, `tm_get_recording`.
- Web UI: Settings page (global default + size/keep limits, all live-saving).
- Web UI: Roster `Rec` column (per-worker on/off; circle filled red when on).

Streaming wiring (caveat — bug observed but not yet fully fixed):
- Recording requires the manager to push PTY bytes to `/pty-out`. The manager
  only does this when it receives a `pty_attach` SSE event, which the hub
  used to fire only on browser WS attach.
- The fix attempts to fire `pty_attach` when recording is toggled on
  (`engine.set_recording_enabled` → `_sync_pty_stream`) and on register if
  recording is on. The hub-side wiring landed but does not appear to be
  reaching the manager for browser-less workers — recordings stay header-only
  for some workers. A pre-existing eviction loop (visible in hub logs as
  `subscribe: evicting 1 existing subscriber(s) for X — duplicate session
  detected`) is suspected to be eating the events. Tracked as open work.

### Cap 7: Settings — SHIPPED (smaller than the plan implied)

Plan said "Cut Admin & Auth UI" because env vars + cert mgmt are infra-level.
What shipped is a tiny Settings page at `frontend/src/App.tsx:SettingsView`
with two purposes:
- Recording defaults (global toggle + size/keep limits) — added with Cap 6.
- Sign-out (clear bearer from localStorage).
No user management, no role-based auth, no cert UI. Consistent with the
single-operator constraint (Premise 5).

## State machine — as it actually ships

Five values, same as planned, with one decay rule added:

| State | Source | When | UI |
|---|---|---|---|
| `unknown` | hub | Worker never registered. | No row. |
| `idle` | hub | No events; trailing event is `outbound` / `permission_response`; **OR trailing `inbound` is older than `BUSY_DECAY_S = 600s`.** | Green badge. |
| `busy` | hub | Trailing event is `inbound` and it's <600s old. | Amber badge + `busy · Xs` counter. |
| `waiting_permission` | hub | `pending_permissions` non-empty. | Purple badge. |
| `offline` | UI-computed | SSE disconnect. Red if not exited cleanly, gray if `exited_cleanly==true`. | Red/gray badge. |

The decay rule was added 2026-04-25 because work orders that complete with
code edits or commits (no channel reply) left workers stuck in `busy`
indefinitely. Tested in `tests/test_bridge_engine.py:test_status_state_decays_old_inbound_to_idle`.

## Architecture as-built — what the hub container looks like

```
browser  ─── WSS /ws/pty/<w>?ticket=…  ─────────▶  hub :8004
        ─── HTTPS /api/workers, /api/permissions, /api/flows,
              /api/settings, /api/workers/<w>/recording, /api/events/stream
        ─── HTTPS /mcp (FastMCP)
                                                    │
                                                    ├── SSE /tubemail/<w>/stream  (forwarder)
                                                    ├── POST /tubemail/<w>/pty-out  (PTY bytes from manager)
                                                    ├── POST /tubemail/<w>/pty-control  (size echo from manager)
                                                    ├── POST /tubemail/<w>/context-pct  (parsed context %)
                                                    ├── POST /tubemail/<w>/register, /goodbye, /outbound,
                                                    │       /permission-request, /permission-response
                                                    ▼
                                            ┌─────────────────────────────┐
                                            │  Worker session             │
                                            │  claude-tm                  │
                                            │  └─ tubemail.manager (pty)  │
                                            │     ├─ tubemail-channel     │
                                            │     └─ claude --name ...    │
                                            └─────────────────────────────┘
```

One container, one port, three protocols (HTTP/HTTPS, SSE, WS). Live-reload
in dev via `./src:/app/src:ro` + uvicorn `--reload`.

## What's worth flagging to reviewers

- **Recording streaming bug**: end-to-end recording works for workers that
  also have a browser tab open; it does not consistently work for browser-less
  workers. Root cause looks like `pty_attach` events being eaten by the
  same SSE eviction loop that flips workers between subscribers in a
  ping-pong pattern (see hub log `subscribe: evicting…`). The investigation
  was paused after a 4-files-per-toggle file rotation flood was observed
  and the rotate-on-re-register behaviour was reverted (re-register no
  longer rotates the recording file).
- **Manager-side context % loop** runs every 3s, parses `context X%` from the
  screen buffer, POSTs only on change. Older managers don't post at all —
  `/api/workers/<w>/update-manager` rolls them.
- **`tm_reconnect_mcp` is fragile**. The deterministic-driving path opens
  `/mcp`, blindly fires N down-arrows, presses Enter, expects "Reconnect" +
  ("Authenticate" or "Disable") to appear within 5s, types `2`, presses
  Enter. Each step is screen-aware in a weak sense (it has a 5s wait for a
  string match). Cursor position is not verified after each arrow, the
  detail-menu detection is brittle, and the "type 2" assumption is wrong
  for non-OAuth servers where Reconnect may be option 1. A planned rewrite
  to be screen-driven at every step was scoped but not started.
- **Settings UI is thin by design**. Three knobs total (recording default,
  max bytes per file, keep N files). If the feature surface grows, this
  page needs structure (sections, descriptions, save-button vs live-save).

## Success criteria — measured against current state

Original v1 success criteria, re-evaluated:

| Criterion | Status |
|---|---|
| See every running worker and its current state | ✓ Roster shipped |
| Approve a Bash permission prompt in ≤2 keystrokes | ✓ Permission Inbox shipped |
| Open an integrated terminal, paste a multi-paragraph work order with Shift+Enter | ✓ TerminalPane + keybinding profile shipped |
| Close every non-web terminal and still do a full day of orchestration | Not formally measured. Operator reports doing this |

Recording-feature acceptance (added):
| Criterion | Status |
|---|---|
| Toggle recording on for a worker, send a command, read the recording back | Partial — works with browser attached, fails for browser-less workers |
| Settings page persists across hub restarts | ✓ HubConfig writes `<data>/hub-config.json` |
| Files rotate at size limit, oldest GC'd | ✓ tested in `tests/test_recorder.py` |

## Open work (not yet scoped into a follow-up plan)

1. Recording streaming for browser-less workers (root cause: SSE subscriber
   eviction loop swallowing pty_attach events).
2. Screen-aware `reconnect_mcp` rewrite — read screen between every keystroke,
   detect cursor position by the `❯` prefix on the active row, parse the
   detail menu rather than assuming option 2.
3. `tm_get_recording` performance with very large frame files — current
   implementation reads every frame to filter; fine at 5 MiB / file but
   would need indexing past ~50 MiB.
